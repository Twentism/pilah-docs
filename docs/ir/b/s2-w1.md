=== "Negative"

    [View](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/features/transaksi/domain/setoran_draft_test.dart#L67-L73)

    ```dart
    test('an item left at zero weight', () {
      final subject = draft(
          items: const [SetoranItemDraft(jenisSampahId: jenis, berat: 0)]);
      expect(subject.problems, contains(SetoranProblem.nonPositiveBerat),
          reason: 'clearing the weight box yields 0 and must not be submitted');
      expect(subject.invalidItemIndexes, {0});
    });
    ```

    This test found a real bug. `num.tryParse('') ?? 0.0` means an emptied
    weight box is `0`, and the old guard never looked. Not a hypothetical bad
    input — it is what happens when a pengelola selects the weight and presses
    backspace.

=== "Corner"

    [View](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/features/transaksi/domain/setoran_draft_test.dart#L101-L113)

    ```dart
    test('zero is rejected and the smallest step above it is accepted', () {
      expect(draft(items: const [SetoranItemDraft(jenisSampahId: jenis, berat: 0)])
          .isValid, isFalse);
      expect(draft(items: const [SetoranItemDraft(jenisSampahId: jenis, berat: 0.1)])
          .isValid, isTrue,
        reason: 'the rule is "more than zero", not "at least one kilo"');

    ```

    Both halves are needed. Without the second, `berat >= 1` would also pass —
    and bank sampah weigh in hundreds of grams, so that reading would quietly
    reject real setoran. The corner case is the pair, not either value alone.

## Test doubles: what is faked, and what it costs

The useful question is not "mock or stub" but **which layer is faked**, because
that decides what the test can still catch.

!!! abstract "The difference, in plain terms"
    A **stub** is a stand-in that *answers*. You wire it in, it hands back a
    prepared reply, and you judge the result by looking at what the app did
    next. A pretend shopkeeper who always sells you the same loaf.

    A **mock** is a stand-in that *remembers*. You wire it in, let the app use
    it, then ask it what it was told to do. A pretend shopkeeper who writes
    down every order so you can check the list afterwards.

    Same idea — something fake where the real thing goes. The difference is
    where you look for the answer: at the app, or at the fake.

### Level 0 — no double at all

[`setoran_draft_test.dart`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/features/transaksi/domain/setoran_draft_test.dart),
14 tests.

**Practically:** nothing is faked. The test hands the rule a nasabah and some
weights and checks the verdict, the way you would check a calculator.

**Implication.** Fast, and they cannot rot — there is no seam to drift. They
also prove nothing about wiring: a correct `SetoranDraft` that no page ever
calls would pass all 14. That is exactly why slice 1 was followed by a page
test asserting no request was sent.

### Level 1 — a stub at the transport boundary

[`stub_api.dart:53`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/support/stub_api.dart#L53-L85):

```dart
class StubApi implements HttpClientAdapter {
  void on(String method, String path, {int status = 200, Object? json}) {
    _routes['${method.toUpperCase()} $path'] = (_) => ResponseBody.fromString(
          jsonEncode(json), status, ...);
  }
}
```

**Practically: a pretend server.** The app genuinely builds its request and
sends it. The request simply never leaves the machine — a canned reply we wrote
is handed back instead.

It is a **stub**, not a mock: it answers, and notes what it was asked, but no
test interrogates *it*. Everything above it is real —
[`transaksi_support.dart:13`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/support/transaksi_support.dart#L13-L23)
builds the genuine cubit, use cases, repository and data source on top of it.
Only the socket is fake.

**Implication, and why this is the default.** Assertions are about *state and
traffic*, not calls:

```dart
expect(api.requests.where((r) => r.method == 'POST'), isEmpty,
    reason: 'a 0 kg setoran must not be sent at all');
```

That sentence is the actual requirement. Had the page test mocked
`TransaksiCubit`, the strongest available assertion would have been
"`addTransaksi` was not called" — true, but one layer from what matters, and
still green if a request escaped by another path.

The cost is real: slower, and they can fail for reasons outside the widget
under test. Here they have repeatedly earned it.

### Level 2 — a mock, for a side effect that leaves the app

[`transaksi_baru_page_test.dart:33`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/features/transaksi/presentation/pages/transaksi_baru_page_test.dart#L33-L35):

```dart
class _MockUrlLauncher extends Mock
    with MockPlatformInterfaceMixin
    implements UrlLauncherPlatform {}
```

**Practically: a stand-in that keeps the receipt.** A test cannot really open
WhatsApp, so a fake takes its place and is asked afterwards: *were you told to
open a link, and which one?*

Installed at
[`:63`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/features/transaksi/presentation/pages/transaksi_baru_page_test.dart#L63),
interrogated at
[`:441`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/features/transaksi/presentation/pages/transaksi_baru_page_test.dart#L441-L443).

**Implication.** Coupled to the shape of the call. Change `launchUrl`'s
signature and it breaks even though behaviour is identical. That is the price
of asking the fake instead of looking at the result, and it is worth paying
only where there is no result to look at.

### Level 3 — a mock to reach a state the stub cannot produce

[`pilih_nasabah_flow_test.dart:121`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/features/transaksi/presentation/widgets/pilih_nasabah_flow_test.dart#L120-L129):

```dart
when(() => broken.loadActiveNasabah())
    .thenAnswer((_) async => throw StateError('rusak'));
```

**Practically: a stand-in told to break on purpose.** The pretend server can
return a 403, a 500 or malformed JSON — all of which arrive as
`NetworkException`. It cannot produce a bare `StateError`. The picker has a
branch for exactly that, and without a mock it is unreachable.

!!! note "Both kinds, in one test"
    The WhatsApp-snapshot test needs a request held open mid-flight *and* needs
    to see which URL was launched. The stub supplies the first
    (`api.latency` — the pretend server answering slowly on purpose); the mock
    supplies the second. Not alternatives: different questions.

### A double that made a test lie

The WhatsApp template comes from
[`profile_support.dart:37`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/test/support/profile_support.dart#L34-L40),
whose default is `'Halo {nama}'`. My first snapshot test asserted the launched
URL contained `'Botol'`. It never could: that template has no item placeholder,
and `{nama}` is not even a key the code substitutes. The test failed before the
fix and would have failed after it — it was not measuring anything.

**A test is only as meaningful as the fixture it runs against**, and a shared
default fixture is a comfortable place for a test to quietly stop testing.

## B2 · Programming principles

**Single Responsibility.**
[`RoleDestinations`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9d8c439/lib/features/main/presentation/widgets/role_destinations.dart#L36-L46)
separates *which* destinations a role has from *how* they are drawn.
[`SetoranDraft`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/lib/features/transaksi/domain/entities/setoran_draft.dart)
does the same for validation: the rules left a 487-line widget and became
testable without building anything.

**Open/Closed.** The rail was added without modifying the bottom bar's render
path — checkable, not asserted: the bar's `build()` output is byte-for-byte
unchanged in that commit, and 18 existing navigation tests passed unedited.
PIL-340 repeated it: `TransaksiCubit`, `ItemSetoranCard` and
`PilihNasabahSection` are untouched across all six slices.

!!! important "The ordering is the actual evidence"
    I extracted the shared destination source *before* writing the rail, as its
    own red-green pair. Written the other way round the diff would look
    similar, but the bar would have been modified and then tidied. Open/Closed
    is a claim about what you *did not have to touch*, which only commit order
    can show.

**Strategy, twice.**
[`NavigationForm.resolve`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9d8c439/lib/design/layout/navigation_form.dart#L26-L35)
picks a navigation form;
[`PickerPresentation.resolve`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9ce14d8/lib/design/layout/picker_presentation.dart#L53-L57)
picks a modal container. One pure function each, interchangeable renderers.

The discriminator differs **on purpose**: navigation is decided by *platform*
(the lead dev's rule — it stays on screen), a picker by *width* (it is
transient, and Material ties it to the window size class). They agree wherever
it matters, since a native phone is always compact. One rule for both would
have been tidier and wrong.

### Two design claims that were refuted

The [programming plan](../../contributions/pil-340.md#what-the-plan-got-wrong)
was written **before** PIL-340's code, so it could be checked afterwards. Of
the three primitives PIL-293 shipped with no call sites:

| Primitive | Outcome |
|---|---|
| `ContentBounds` | Adopted |
| `MasterDetailLayout` | Refuted — splits at 600 where the form needs 840; proportional panes where a summary wants a fixed 340px |
| `PageStateView` | Refuted — deliberately hides stale content, which on a form blanks what the user just typed |

One for three. The honest lesson is about the bet: **shipping a primitive
before its first caller means designing against an imagined screen.**

## B6 · Security

Three distinct OWASP items named in commit bodies this week.

| Item | Where | Mine or cited |
|---|---|---|
| **A01** Broken Access Control | PIL-293 and PIL-340 | mine |
| **A04** Insecure Design | PIL-340, five commits | mine |
| **A05** Security Misconfiguration | PIL-340 — the CORS finding | cited; reported, not fixed here |

**A01.** One source of truth for role-to-destination mapping, so adding a
second *or third* navigation surface cannot widen any role's menu.
[`forRole`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/9d8c439/lib/features/main/presentation/widgets/role_destinations.dart#L36-L46)
fails closed — an unrecognised role gets `const []`, not the staff menu — and
rail and drawer both render nothing without a session. In PIL-340 the price box
became `canRequestFocus: false` rather than merely `readOnly`, so price stays
entirely server-owned with no keyboard path to it.

!!! important "Defense in depth, not the control"
    A UI that hides a menu item is not access control. The real control is
    server-side authorization plus the router redirect, and the commit bodies
    say so: *"Kontrol akses sebenarnya tetap di server dan redirect router; ini
    lapisan UI."*

**A04.** One guard, `problems.isNotEmpty` in `_handleSubmit`, which both entry
points pass through — the button and Enter. Adding a keyboard route to an
action that moves a nasabah's balance meant moving the guard into the handler
rather than duplicating it. The in-flight freeze closes the window where stored
and reported truth could differ.

**A05.** Web could not save a setoran at all. `POST /api/v1/transaksi` carries
an `Idempotency-Key` header; `CORS_ALLOW_ALL_ORIGINS=true` permits any origin
but not arbitrary headers, so the browser never sent the request — the backend
log showed `OPTIONS … 200` with no `POST`. Never seen before because **CORS is
browser-only** and the native app sends no preflight. Reported; patched locally
and left uncommitted at the team's request.

!!! warning "A08 is in the code but is not claimed"
    The success screen shows the server's `totalNilai` and `saldoSetelah`, not
    the form's arithmetic — a genuine integrity protection, and the plan had
    listed A08 among five. I did not name it in a commit body, and the
    criterion asks for the commit message. Back-filling it afterwards would
    defeat the point of choosing the item while planning the slice, so it is
    recorded as a miss. **Three, not five.**

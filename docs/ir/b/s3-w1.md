## B2 · Programming principles

Three design patterns, each in its own commit so the diff is linkable, and each
chosen by a force in the problem rather than fitted to the code afterwards. All
three belong to PIL-432, which is where the week's real difficulty was.

=== "mobile #186 — Factory Method and Template Method"

    **Factory Method — the design system makes a route without naming one.**

    `SideSheetPage` extends Flutter's `Page<T>`, which declares
    `Route<T> createRoute(BuildContext)` and leaves the concrete product to the
    subclass. `SideSheetPage` overrides it to return `_SideSheetRoute<T>`: the
    framework owns the creator, the subclass decides what gets instantiated,
    and nothing holding a `Page` has to know which route it will become.

    The force that chose it is a dependency rule rather than taste. The panel
    lives in `lib/design/`, and the design system must not depend on the router
    package the app happens to use. A plain framework `Page` is usable by
    go_router's declarative page list **and** by a bare `Navigator.push`, which
    also makes the route testable without building a router at all.

    | Considered | Verdict |
    |---|---|
    | go_router's `CustomTransitionPage` | **Rejected.** It does the same job in fewer lines and binds `lib/design/` to go_router. A design-system primitive that works under only one router is not a primitive. |
    | `showGeneralDialog` on the root navigator | **Rejected, after being chosen first.** It was the original container, and the browser disproved it: a dialog opened straight onto the navigator never enters go_router's page list, so it creates no history entry and the browser's back button reaches past it. See [B7](#where-it-was-wrong-and-how-it-was-caught). |

    **Template Method — the route keeps the page behind it alive.**

    `_SideSheetRoute` extends `PageRoute<T>`. The algorithm for installing,
    animating and popping a modal route belongs to `TransitionRoute` and
    `ModalRoute`; the subclass fills in the hooks they call — `opaque`,
    `barrierDismissible`, `barrierColor`, `barrierLabel`,
    `transitionDuration`, `buildPage` and `buildTransitions`.

    One of those hooks is the whole ticket:

    ```dart
    @override
    bool get opaque => false;
    ```

    An opaque route lets Flutter stop painting, and eventually unmount,
    whatever is underneath it. The entire reason this panel exists is that the
    page behind it must stay visible, so `opaque => false` is not a style
    choice; it is the requirement expressed as one override. The pattern is
    what makes that cheap. A container owning its own algorithm would have to
    re-implement barrier handling and the pop lifecycle before it could change
    that single answer.

    | Considered | Verdict |
    |---|---|
    | A persistent `Overlay` entry plus shared state | **Rejected.** Closest to Material's own non-modal side sheet, but an overlay is not a route: no back-button integration, and a page left interactive behind a live form can navigate away mid-submit. |

    Both patterns arrive in [`7655eacc`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/7655eacc) `fix(design)`: make the side sheet a declared route so browser back closes it.

    !!! note "One piece of this branch is deliberately given no pattern name"
        `SideSheetGuard` holds a one-shot latch and is shared by two exit paths
        that do not know about each other — `PopScope`, which only
        `Navigator.maybePop` consults, and `GoRoute.onExit`, which is the only
        hook a browser history traversal passes through. One object, because
        two would ask twice about a single close.

        It is the most interesting object here and it is not a GoF pattern.
        Calling it a Mediator because it sits between two collaborators would
        be padding the count, and the criterion asks for *different cases*, not
        for more labels.

=== "mobile #195 — Strategy"

    **Strategy — one form, three ways of leaving.**

    `SetoranFormView` was extracted out of the 613-line `TransaksiBaruPage`. It
    has no `Scaffold`, builds no header, and never pops a route. Both the
    header widget and the close behaviour arrive as constructor parameters, so
    the container supplies the policy and the content merely runs it:

    | Container | The `onClose` it injects | Why that one |
    |---|---|---|
    | `TransaksiBaruPage`, full screen | `context.pop()` | go_router owns the page, so popping it is correct. |
    | The panel's header close button | `Navigator.of(sheetContext).maybePop()` | `maybePop` is the only pop that consults `PopScope`, so this exit passes through the unsaved-input guard. A close button is an exit that gets hit by accident. |
    | The panel, after a successful save | `allowNextExit()` then `Navigator.of(sheetContext).pop()` | The user has already decided. Asking here would hold up the save they just asked for. |

    The form knows none of the three, and must not: `GoRouter.pop()` called
    from inside the panel pops the page *behind* the panel, because the panel
    is pushed onto the navigator rather than matched by the router. Injecting
    the exit is what makes that mistake unavailable to the content.

    | Considered | Verdict |
    |---|---|
    | A container `enum` on the form plus a branch at each exit | **Rejected.** It puts the container's knowledge back inside the content, and the widget could then be tested only through its containers. |

    The extraction is a `refactor` commit separate from everything that uses
    it, and its claim to change no behaviour is checkable rather than asserted:
    **423 existing tests stayed green with zero test edits.** Commits [`d248292c`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/d248292c) `refactor(transaksi)`: extract SetoranFormView from TransaksiBaruPage and
    [`0b3dd860`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/0b3dd860) `refactor(transaksi)`: move SetoranFormView to its own file.

=== "mobile #202 — no pattern, and that is the answer"

    PIL-436 removes entry points. There is no pattern in it, and none is
    claimed.

    The one piece of structure it does add is worth a sentence, because it is
    design and not a pattern: the four locked URLs are **derived by looping one
    exported route list** rather than retyped next to it, so the redirect paths
    cannot drift from the real ones. A test asserts exactly that. That is a
    single source of truth, which is a principle; calling it a pattern would be
    reaching.

=== "Why PIL-432 is two pull requests and not one"

    PR 1 is the design-system primitive; PR 2 adopts it. They could have been
    one branch, and splitting them costs something real: on a stacked base
    SonarCloud measures both diffs as new code, and retargeting PR 2 after PR 1
    merges will rebase it and orphan its commit hashes.

    They are split because the primitive is reviewable on its own terms — a
    container rule, a width rule and a guard, with 44 tests and no feature
    attached — while the wiring is a different review entirely, about which
    call sites change and what breaks. A reviewer who has to hold both at once
    reviews neither.

    The decision to **stack** them rather than merge PR 1 first was made after
    those costs were laid out, so review of PR 2 could begin while PR 1 waited
    on a human. One predicted cost did not materialise: Sonar analysed the
    stacked pull request normally on this repository.

## B6 · Security

requests, so none is claimed as written.** The slice had been planned as A01
broken access control at level 1 — the panel must not open for a non-Pengurus
role — and it was not delivered. Saying so is the point of the convention this
project works to: a claim is only ever as good as what the commit says, and a
criterion with nothing behind it is left empty rather than filled with an

### Where it was wrong, and how it was caught

- **The plan's most load-bearing verified fact was stale by the time it was
  used.** The PIL-432 plan turned on seven cubits being provided above
  `MaterialApp.router`, verified by reading the file. Overnight, PIL-377
  replaced Bloc with Riverpod and the `MultiBlocProvider` ceased to exist. The
  conclusion survived — `ProviderScope` still wraps the router, so a
  root-navigator route still sees every provider — but it survived by luck, not
  by method. The user caught it and said so: *"wait so why the plan's biggest
  verified fact was stale?"* A fact verified on day one and used on day two has
  to be re-verified, especially in a repository where `staging` moved forty
  commits in two days.

- **A test seam that production could not use.** The platform was first
  injected into `SideSheetPresentation.resolve` through an
  `@visibleForTesting isWebOverride` parameter. That annotation means precisely
  *production must not pass this*, while `kIsWeb` being a compile-time constant
  means production is exactly what has to pass it. The project's existing idiom
  was already the plain explicit argument, in `NavigationForm.resolve`. Fixed
  in
  [`c9d3be17`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/c9d3be17)
  to a plain optional `isWeb` defaulting to `kIsWeb`. The annotation read as
  the tidy, disciplined choice and was a back door.

- **A claim in the pull request body that the browser disproved.** PR 1
  justifies its container with "a real route: Esc, browser back and
  `Navigator.pop` all close it". Driving the built app showed browser back does
  not close it, and does something worse: a `showGeneralDialog` route on the
  root navigator creates no history entry at all — `history.length` stayed at
  4 and the URL never changed — so back popped the page *underneath*, the shell
  navigated from the dashboard to the login screen, and the half-typed setoran
  was gone. The claim was already sitting in a pull request awaiting review.
  Two commits were needed, because the first fix only moved the problem:
  [`7655eacc`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/7655eacc)
  made the panel a declared route, so back closes the panel instead of the
  page, and back still skipped the discard guard, because `PopScope` is only
  consulted by `Navigator.maybePop` while a history traversal removes the page
  declaratively.
  [`9bbee7d7`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/9bbee7d7)
  closes it with `GoRoute.onExit`. Both halves were measured on screen with the
  dirty state visible, not reasoned about.

- **A test that could pass while proving nothing.** The platform gate has a
  native case and a web case. Under the Dart VM, `isWeb: false` and *no
  plumbing at all* are indistinguishable, so the native test would have passed
  against a version where the argument was never threaded through. The wide
  **web** case is the one that pins the wiring; the native case only guards the
  gate. Both are kept, and which one is doing the work is now written down.

- **A superseded CI run read as a failure.** Two pushes in quick succession
  leave two workflow runs against one pull request, and
  `gh pr view --json statusCheckRollup` lists jobs from both. The older run's
  jobs show `SKIPPED` because the newer run cancelled them, and read mid-flight
  that looked like SonarCloud being suppressed by the stacked base. It was not;
  Sonar ran and passed on both pull requests. Reading a rollup instead of the
  newest run is the same mistake as reading a green tick instead of the issue
  count.

- **A build reported as blocked that was not.** An earlier week recorded the
  Android debug APK as unbuildable on this machine. It builds. `JAVA_HOME`
  pointed at an Adoptium **JRE**, which carries no compiler, while a real JDK
  21 was installed alongside it; prefixing the build with the JDK path works.
  That is a correction of my own earlier claim, and it matters because the
  claim had been used as a reason to skip native verification.

- **A checklist I wrote that named the wrong tool.** The hand-off commands for
  the user's own terminal said `dart` and `flutter` bare. On this machine those
  resolve to a second, older Flutter install — Dart 3.9.2 against the 3.11.1
  the project needs — and the failure blames a package rather than the
  toolchain, so it reads as a dependency problem. The user hit it. Instructions
  handed to a person now carry the full SDK path.

- **Two findings from the review on PIL-436, both taken.** The claim that the
  Pengumuman feature stayed restorable was too narrow: the feature's own test
  suites guard its *pages*, but the **route-level** guards went out with the
  builders — the detail row fallback, the form's argument fallback, and the
  `keanggotaan_id` without which a nasabah belonging to two banks gets a 422 —
  along with the two tests that pinned them. Fixed in
  [`b6058f2a`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/b6058f2a),
  which keeps those three routes compiled and tested but unregistered, and
  builds the redirect locks by looping that same list so the locked paths
  cannot drift from the real ones. The second finding was about framing: the
  Nasabah removal had been justified by handover scoping when the parent
  acceptance criterion settles it directly and is role-neutral. The pull
  request body was corrected and credits the reviewer.

- **Screenshots missing from a pull request body, reported by a teammate
  rather than noticed.** Relayed by the user: *"he added that you haven't put
  the playwright screenshots in the PR description!!"* The mobile `AGENTS.md`
  requires them for user-visible web changes. The rule was in the file, the

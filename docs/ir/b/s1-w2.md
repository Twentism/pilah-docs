## B1 · Test-driven development

PIL-214 on 25 September is the clearest single run of red-green-refactor in the
project — nine cycles, each one behaviour:

```
red(nasabah): the list API's paging metadata is thrown away
green(nasabah): read count and next from the list API
red(nasabah): there is no way to reach the pages after the first
green(nasabah): append the next page on demand
red(nasabah): nothing asks for the next page while scrolling
green(nasabah): request the next page as the list nears its end
red(nasabah): typing only searches the page already loaded
green(nasabah): search the whole list on the server
red(nasabah): the tab filter never reaches the server
green(nasabah): send the selected tab to the server
...
refactor(nasabah): read the paged response in one place
refactor(nasabah): drop the unreachable bare-list branch
refactor(nasabah): rename the page entity so it stops colliding with the screen
```

**Corner case.** `test(nasabah): cover the two-character search boundary` —
search only hits the server at two characters or more, so one character and two
characters are the on-point and off-point pair. A test at "budi" would pass
whichever threshold was coded.

**A test that was deleted rather than kept.**
`refactor(nasabah): drop the unused empty page constant` and
`drop the unreachable bare-list branch` both removed code the paging rewrite
had orphaned. Coverage that exists only to cover dead code is worse than no
coverage, because it makes the dead code look load-bearing.

## B2 · Programming principles

**Dependency Inversion.** `refactor(nasabah): let the page delegate its list to
the paged widget` — the screen stopped owning list mechanics and started
depending on a widget that does. The screen got shorter and the behaviour got
reusable.

**Single Responsibility.** `refactor(nasabah): rename the page entity so it
stops colliding with the screen` is a naming fix, but the collision was the
symptom: one word, `Page`, meant both "a screen" and "a slice of results". Two
responsibilities sharing a noun.

**Interface Segregation, by accident then on purpose.**
`red(nasabah): the list can only ever be fetched one way` → `green(nasabah):
let the caller pick the page, tab and search term`. The picker in the transaksi
flow and the nasabah admin screen want different slices of the same data, and
forcing one fetch shape on both is what had gone wrong.

## B6 · Security

**A01 · Broken Access Control** — *mine.*

PIL-223 and PIL-288 are both about *who may change what*, and they resolve to
the same shape: **the server decides, the client reflects.**

Once a nasabah has their own account, the pengurus loses the right to edit
their personal data. Enforced server-side with a 403; the app renders the form
read-only so the pengurus is not invited to make a change that will be refused.

One detail that matters, and that a naive implementation gets wrong: the 403
fires only when a locked value **differs** from what is stored. Submitting an
unchanged locked field is not an attempt to change it, and refusing it would
break every ordinary save.

```
green(nasabah): tolak nomor HP yang bentrok di bank sampah lain
green(nasabah): tulis perbaikan profil pengurus ke akun pemiliknya
green(nasabah): kunci email saja pada profil nasabah berakun
```

The scope narrowed mid-ticket — from "lock the whole profile" to "lock only
`email`" — because `email` was about to become the account-linking key in
PIL-154. Locking the rest would have been correct-looking and wrong, for a
reason invisible in the code.

## B7 · AI literacy

This is the week the AI assistant's output stopped being taken at face value.
An asserted merge conflict between two PRs turned out not to exist —
`git merge-tree` showed a clean merge. The lesson was not "it was wrong" but
**"it inferred when one command would have checked"**, which became the most
common correction category across the whole project.

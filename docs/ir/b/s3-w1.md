## B4 · Peer review

Two reviews on the two halves of one ticket — customer search by full or
partial ID, backend and Flutter. Each carries a positive point, a problem
verified in the code before it was written up, and a concrete fix. Both
findings are performance findings, which is the level the criterion reserves

The two halves share a root cause, which is why reviewing them together was

### backend #132 — alghani46, search customers by full or partial ID

Adding `nomor` to the existing OR group rather than to the outer filter is the
right call, and the test that pins it is the valuable one:
`test_search_id_never_exposes_other_bank_even_with_same_id` creates the *same*
`nomor` in a second bank and asserts only the caller's row comes back, so the
new predicate provably cannot widen the access boundary. Rebuilding the
predicate as a named `search_filter` with one field per statement also reads
better than the old chained expression.

**The search path now does four unindexable scans per request, twice over.**
Production runs PostgreSQL (`DB_ENGINE=django.db.backends.postgresql` in
`.github/workflows/deploy-cloud-run.yml`), where:

- `icontains` compiles to `UPPER("nasabah"."nomor"::text) LIKE UPPER(%s)` with
  a leading `%`. The function call *and* the leading wildcard each
  independently rule out a b-tree. The only index covering `nomor` is the
  `unique_together ("bank_sampah", "nomor")` b-tree, usable for equality or
  prefix on the raw column and never for `%…%`.
- So a list request evaluates up to four `UPPER() LIKE '%…%'` predicates
  against every row in the bank's partition.
- `StandardPagination` (`PageNumberPagination`, `PAGE_SIZE = 20`) then issues
  `COUNT(*)` over the same filter before slicing the page, so that scan runs
  **twice per request**.
- `ORDER BY nomor` over the filtered set becomes a sort rather than an index
  walk, since the `(bank_sampah, nomor)` index is unusable once the OR group is
  in play.

The PR's own findings table reaches the same place — "Four substring predicates
and count queries may be costly … measure query plans and indexing needs" — but
defers it without a remedy, and this is the change that makes ID search, long
and digit-heavy, the common case rather than the rare one.

The fix was offered in two tiers so the author can take either.

**Index the substring search properly.** `pg_trgm` GIN is the only index type
that accelerates `%…%`, and because `icontains` wraps the column in `UPPER()`
the index expression has to match it:

```python
# apps/nasabah/migrations/00XX_nasabah_search_trgm.py
from django.contrib.postgres.indexes import GinIndex, OpClass
from django.contrib.postgres.operations import TrigramExtension
from django.db import migrations
from django.db.models.functions import Upper


class Migration(migrations.Migration):
    operations = [
        TrigramExtension(),
        migrations.AddIndex(
            model_name="nasabah",
            index=GinIndex(
                OpClass(Upper("nomor"), name="gin_trgm_ops"),
                name="nasabah_nomor_trgm_idx",
            ),
        ),
        # and the same for nama
    ]
```

with `django.contrib.postgres` added to `INSTALLED_APPS`. One caveat was given
with it rather than left for the author to discover: trigram indexes need
**three** characters to be selective and the search minimum is two, so a
`test_two_character_id_fragment_is_searched`-shaped query still falls back to a
scan. Raising the minimum to 3, or routing 2-character queries to
`istartswith`, closes that gap.

**Zero-migration version, if the extension is too much for this PR** — stop
running four predicates when the query shape already rules three of them out:

```python
if self.action == "list" and len(search) >= 2:
    if "@" in search:
        search_filter = Q(email__icontains=search)
    elif search.isdigit():
        search_filter = Q(nomor__icontains=search) | Q(no_hp__icontains=search)
    else:
        search_filter = Q(nama__icontains=search) | Q(nomor__icontains=search)
    qs = qs.filter(search_filter)
```

This was checked against their test file before being suggested, and it keeps
every case green: `000123` and `0012` are digits, so nomor + no_hp; `11110001`
hits the phone branch; `budi@example.test` hits email; `zx-999` and `budi` fall
through to nama + nomor, which is what
`test_query_matches_different_fields_without_duplicate_customers` needs. It
halves the per-row work with no extension and composes with the index later.

Also asked for: an `EXPLAIN (ANALYZE, BUFFERS)` for `status=aktif&search=0012`
against the 102-row demo set, pasted into the PR. At that size every plan looks
fine, which is exactly why the number is worth recording now rather than after
a bank imports a few thousand customers.

**Small nit:** `len(search) >= 2` counts raw characters, so a query of two
spaces passes the gate and runs the full four-predicate filter plus `COUNT(*)`
for a query that can only match incidentally. `search.strip()` before the
length check costs nothing.

### mobile #168 — alghani46, clarify customer ID search on mobile and web

Collapsing the hint into one `nasabahSearchHint` consumed by
`nasabah_page.dart`, `nasabah_table.dart` and `nasabah_search_bar.dart` is the
right shape — those three had already drifted into "Cari nama nasabah..." and
"Cari nama atau nomor...", and now they cannot drift again. The layout test is
also the good kind of corner case: a 30-character legacy ID at 390x844
asserting `maxLines: 1`, ellipsis, the ID below the name and at least 8px clear
of the balance. That is the model column limit rather than a comfortable
fixture. Extending the semantics assertion to `contains('ID: NAS-0002')` means
the new row reaches screen readers instead of only being painted.

**Superseded searches are discarded on the client but still executed in full on
the server, and this PR makes that the normal case rather than the exception.**
`searchNasabah` cancels `_jedaCari` and bumps `_listRequestGeneration`, and
`loadNasabah` drops the stale response at
`requestGeneration != _listRequestGeneration`. That protects correctness, and
the generation counter is the right mechanism for it. What it does not do is
stop the work: `NetworkService.get` accepts only `queryParams` and `headers`
and never a Dio `CancelToken`, so once the 300 ms pause has fired a request,
the HTTP call and the backend's four-`icontains` scan plus `COUNT(*)` run to
completion and the result is thrown away. `RetryInterceptor` compounds it — per
its own comment it "quietly retried once before the failure reaches state
handling" — so a superseded request that gets dropped can cost two backend
searches for a page nobody will ever see.

This matters more after the change than before it. Names are short and typed in
one burst; IDs like `NAS-0000000000000123` are long and typed with hesitations,
so a single ID lookup plausibly fires two or three full searches where a name
search fired one. The PR description already notes the notifier "does not
cancel database work already in flight" — that is the hook to actually do it.

The fix threads a `CancelToken` down the path the author already owns:

```dart
// lib/core/client/network_service.dart
Future<Response> get(
  String path, {
  Map<String, dynamic>? queryParams,
  Map<String, String>? headers,
  CancelToken? cancelToken,
}) async {
  ...
  Response response = await dio.get(
    environment.baseUrl + path,
    queryParameters: queryParams,
    cancelToken: cancelToken,
    options: options.copyWith(headers: headers ?? headersRequest()),
  ).timeout(globalTimeout);
```

then `final CancelToken? cancelToken;` on `GetNasabahParams`, passed through
`GetNasabahUseCase` to the repository and datasource, and in the notifier:

```dart
CancelToken? _pencarianBerjalan;

void searchNasabah(String query) {
  if (_searchQuery == query) return;
  _pencarianBerjalan?.cancel('kata kunci diganti');
  _pencarianBerjalan = CancelToken();
  _searchQuery = query;
  ...
}
```

Two traps were named with it, because both are the kind that turn a performance
fix into a bug: map `DioExceptionType.cancel` to a no-op in the failure
handling so a cancellation never paints `NasabahError` over a live list, and
make `RetryInterceptor` skip cancelled requests, or it will re-fire exactly the
request that was just cancelled.

**A second, cheaper one.** `_refreshActiveCount()` calls
`getNasabahUseCase.execute(const GetNasabahParams(status: 'aktif'))` and then
reads only `data.totalCount`, so it downloads a 20-row page with each row's
`saldo` serialized in order to display one integer.
`GetNasabahParams(status: 'aktif', pageSize: 1)` returns the same `count` for a
twentieth of the payload. It is on the search path too, via
`_reloadAfterMutation` whenever `_searchQuery` is non-empty.

**Nit:** the hint drops email, which the backend still matches
(`Q(email__icontains=search)`, kept for compatibility per the companion PR).
Reasonable as a deliberate simplification, but a Pengurus who pastes an email
will get results the hint says they should not — worth a line in the
description so nobody later "fixes" the backend predicate to match the hint.

    These are two reviews, not one review restated. The backend finding is

    requests get issued for a single lookup. Either fix alone helps: the

### What the history shows, including where it was steered

- **The premise of the first prompt was wrong, and saying so changed the
  work.** The question assumed the search had to be for PRs *from the S2W3
  window*. B4 evidence is dated by when the review is posted, not by when the
  PR was opened, so that filter bought nothing and biased the choice toward
  the stalest PRs. The reply said so before answering, then answered both the
  question asked and the question behind it.
- **Two findings were nearly asserted without being checked.** The obvious
  review comment on a `%…%` search is "this is slow, add an index". That claim
  only holds on this project if production is PostgreSQL and no usable index
  exists, so both were verified — `deploy-cloud-run.yml` for the engine, the
  model's `unique_together` for the index — before a word of the review was
  written. The zero-migration alternative was likewise checked against the
  author's own test file first, because a suggestion that turns their suite red
  is not a feasible suggestion.
- **The local checkout was pinned to an old commit, and reviewing it would have
  reviewed the wrong code.** The mobile submodule sat at a commit predating the
  `providers/` refactor, so the notifier under review did not exist locally.
  The files were fetched from the PR head instead. This is the kind of mistake
  that produces a confident review of code nobody wrote.
- **A direction was given and followed exactly**: record the comment content in
  the docs, with no comment dates and no links. The s3-w1 page does that, and
  the one place it goes further — naming each PR in plain text so the claim can
  be checked — was flagged rather than assumed.

# PIL-340 — recording a setoran on the web

**[PR #72](https://github.com/bank-sampah-PILAH/pilah-mobile/pull/72)** · 23 commits ·
six slices · targets `staging`

Recording a setoran is the one thing the Pengurus web dashboard exists to *do*.
Every other screen reads; this one writes, moves a nasabah's balance, and sends
them a message about it. It is built on the responsive shell from
[PIL-293](pil-293.md) and consumes the primitives that shipped with it.

## The six slices

| # | Slice | What it changed |
|---|---|---|
| 1 | Validation as a value object | `SetoranDraft` / `SetoranItemDraft` — submission rules testable without building a widget |
| 2 | Two-column form | Fields left, summary and save in a fixed 340px panel right, on expanded windows |
| 3 | Nasabah picker | Bottom sheet on a phone, centred dialog in a browser |
| 3b | Live validation | A cleared weight reddens at once; a blocked save raises a notification |
| 4 | Save in flight | Form frozen during the request; WhatsApp draft snapshotted before the await |
| 5 | Keyboard | Enter submits from the weight box; Tab skips the read-only price box |
| 6 | Success confirmation | Bottom sheet on a phone, centred dialog in a browser |

Slice 3b was not in the plan. It came from the lead dev reviewing slice 3 in a
browser and saying the error should appear *before* the save button is pressed.

## Three bugs the tests found

None of these came from reading the code. Each one came from writing a test
that asked a question the code had not been asked before.

### A 0 kg setoran was being sent to the server

`ItemSetoranCard` parses its weight box with `num.tryParse(value) ?? 0.0`, so
clearing the box yields `0`. The submit guard checked that a nasabah was
chosen, that the list was not empty, and that each item had a jenis — but never
that the weight was above zero.

The backend rejects it (PIL-224), so this was never a data hole. It was a round
trip and a server error where inline feedback belongs.

### The summary overflowed on every real phone width

`TransactionSummarySection` put a label and an amount in a `Row` with neither
flexible. The existing page tests ran on an 800px surface, so nothing had ever
exercised it at a phone width. At 390 it overflowed by 72px; at 320, by 182px.

Pre-existing, and not from this branch — confirmed with
`git log feature/pil-293..HEAD -- <file>`, which was empty. Fixed by scaling the
figure down rather than ellipsising it:

```dart
// Nominal uang tidak boleh dipotong atau diberi elipsis, jadi
// ketika ruangnya kurang angkanya dikecilkan, bukan dipangkas.
Flexible(
  child: FittedBox(
    fit: BoxFit.scaleDown,
    alignment: Alignment.centerRight,
    child: Text(_formatCurrency(grandTotal), maxLines: 1),
  ),
),
```

A truncated money figure still looks like a money figure. That is the reason
for `scaleDown` over `TextOverflow.ellipsis`.

### The WhatsApp draft could describe a setoran the server never saw

The most interesting of the three, because the code already *claimed* to handle
it. `buildWaSetoranLink` carried this comment:

> Built here, before the sheet opens, so the draft is a snapshot of what was
> actually submitted rather than of whatever the form holds by the time the
> pengelola taps the button.

It is built after `await cubit.addTransaksi(request)` and reads
`selectedCustomer` and `setoranItems` as they are *then*. Since `_isSaving` only
disabled the save button, every other control stayed live during the round trip.
Delete an item mid-request and the nasabah receives a message describing a
setoran that was never stored.

Closed from both sides, because they fail differently:

- the inputs are **copied before the await**, which is a property of the data
  and stays true regardless of the UI;
- the form is **frozen during the request** with `AbsorbPointer`, which is a
  property of the UI and stops the pengelola believing their edit was included.

!!! note "A comment is not a guarantee"
    The comment was accurate about intent and wrong about the code, and it had
    been sitting there being reassuring. A test asking "what if the form
    changes during the request?" took ten minutes to write.

## What the plan got wrong

The [programming principles](../process/programming.md) page stated PIL-340's
claims before any of it was written, so they could be checked afterwards. Two
were wrong.

PIL-293 deliberately shipped three layout primitives with no call sites, on the
argument that PIL-340 would adopt them. The scoreboard:

| Primitive | Outcome |
|---|---|
| `ContentBounds` | **Adopted.** Wraps the form body. |
| `MasterDetailLayout` | **Refuted.** Splits at medium (600) where the form needs expanded (840); panes are proportional where a summary panel wants a fixed 340px; and a summary is an always-present aggregate, not the detail of a selected row. |
| `PageStateView` | **Refuted.** Built for a page loading data, and it deliberately hides stale content behind skeletons. On a form that means blanking out what the pengelola just typed. `empty` has no meaning for a save, and a failed save is better served by a notification that leaves the form intact to retry. |

One of three. The honest reading is that shipping primitives ahead of their
first caller is a bet, and this one mostly lost — a widget with no call site is
designed against an imagined screen rather than a real one.

`MasterDetailLayout` is still right for a genuine list-and-detail screen
(PIL-337+). It was not wrong to build; it was wrong to predict *this* ticket
would use it.

## What held

- **`TransaksiCubit`, `AddTransaksiUseCase` and `TransaksiRepository` are
  untouched** across all six slices. The named risk in the plan — that the
  layout rework would force changes into the cubit — did not materialise.
- **Every pre-existing picker and page test passes unedited.** Two widgets
  gained optional parameters with defaults (`BottomSheetHeader.showDragHandle`,
  `ItemSetoranCard.onSubmitted`), so no existing caller changed.
- **Strategy appeared again**, unplanned: `PickerPresentation.resolve(width:)`
  picks a container, `showAdaptivePicker` and `showAdaptiveConfirmation` apply
  it. Same shape as `NavigationForm` in PIL-293.

!!! important "The same pattern, a different discriminator — on purpose"
    Navigation is decided by **platform**: the lead dev's rule is that the bar
    sits at the bottom in the app and the navigation sits on the left in a
    browser, because it stays on screen.

    A picker is decided by **width**, because it is transient and Material ties
    it to the window size class.

    The two agree everywhere it matters, since a native phone is always compact.
    Writing one rule for both would have been tidier and wrong.

## A blocker that was not ours

Saving from a browser failed with a generic error toast. The backend log showed
the shape of it immediately:

```
"OPTIONS //api/v1/transaksi HTTP/1.1" 200 0
"OPTIONS //api/v1/transaksi HTTP/1.1" 200 0
```

Four preflights, no `POST`. The browser was refusing to send the request.

`POST /api/v1/transaksi` carries an `Idempotency-Key` header.
`CORS_ALLOW_ALL_ORIGINS=true` permits any *origin* but not arbitrary *headers* —
django-cors-headers answers the preflight with its own default list, which does
not include it. `CORS_ALLOW_HEADERS` is set nowhere in `pilah-be`: not in
settings, `docker-compose.yml`, `fly.toml` or the Cloud Run environment.

The part worth keeping is **why it had never been seen**: CORS is a
browser-only mechanism. The native app sends no preflight, so the header always
sailed through. Web is simply the first client to send it.

Reported to the team, who confirmed it was already being handled alongside an
in-progress web deployment, and asked for a local-only fix. Patched locally and
left uncommitted; a real `POST /api/v1/transaksi` then returned **201**.

```
flutter build web --release -t lib/main_development.dart # Built build/web
```

The seven failures are `onboarding_flow_test.dart`, which fail only locally for
`.env` reasons and pass in CI. Unchanged in count and identity throughout.

Browser QA with Playwright as Pengurus at 1440×900 and 390×844, against the
running backend. CI green, SonarCloud **0 open issues**.

Two notes on how that was run, because both are easy to get wrong:

- The **release build was served and confirmed to render**, not merely to
  compile. A green `flutter build web` has produced a blank white page on this
  project before.
- The **authenticated pass ran on the debug server**, because `!kReleaseMode`
  strips the demo login from a release build, so there is no way to sign in to
  a local release build without a real Google client ID.

    The APK builds and the phone paths are covered by tests, but nothing has run
    on a physical device. Stated in the PR rather than left implied.

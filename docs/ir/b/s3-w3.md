### The vacuous test, which is the strongest B1 item this week

One existing case asserted that `find.bySemanticsLabel('TANGGAL LAHIR, wajib
diisi')` was absent. It passed, and it could not have failed: in that sheet the
caption is drawn through a widget that **has no required marker at all**, so no
field there could ever produce that label. The test was green over any
implementation, including a wrong one.

It is replaced by a contrast that can actually fail: an empty nama refuses and
an empty tanggal lahir does not, asserted in the same case.

```dart
expect(key.currentState!.validate(), isFalse);
expect(find.text('Bagian ini wajib diisi.'), findsOneWidget);
expect(find.text('Tanggal lahir wajib diisi'), findsNothing);
```

The reviewer's own suggestion, asserting the visible marker, would have been
another vacuous test for the same reason: the pengurus sheets mark nothing as
required. That is worth stating, because the fix is not "do what the reviewer
said" but "do the thing the reviewer was pointing at".

This is the fourth test on this project found to pass over code it was not
testing, and it is the reason row 2 of the
[correction tally](../part-b.md#b7-how-i-use-ai) exists.

**The cases, two tests in
`tests/regression/identity/test_csp.py`:**

| Kind | Case | What it pins |
|---|---|---|
| Negative | *subsumber swagger disematkan pada satu versi* | The `@latest` string is absent from the rendered page. The thing that must **not** be there. |
| Positive | *docs memberi integrity pada setiap subsumber luar* | Every external script and stylesheet tag carries `integrity="sha384-..."` and `crossorigin="anonymous"`, asserted per tag with `subTest`. |
| Corner | the favicon is excluded, by `rel="icon"` | A favicon is not an executable subresource and has no integrity mechanism, so requiring one would be requiring something that does not exist. The exclusion is in the test rather than in a comment. |

!!! tip "The integrity test carries a guard against being vacuous, which is this page's other theme"
    A loop that asserts something about every matching tag passes trivially
    when nothing matches, which is **exactly** the shape of the mobile test
    found and replaced [above](#the-vacuous-test-which-is-the-strongest-b1-item-this-week).
    So the test asserts the list is not empty before it walks it:

    ```python
    tag_luar = [tag for tag in re.findall(SUBSUMBER_LUAR, body) if 'rel="icon"' not in tag]
    self.assertNotEqual(tag_luar, [], body)
    for tag in tag_luar:
        with self.subTest(tag=tag):
            self.assertRegex(tag, r'integrity="sha384-[A-Za-z0-9+/]+={0,2}"')
    ```

    Without that one line, deleting every CDN tag from the template would make
    the test pass. The failure message is handed the whole response body on
    purpose, so a future failure shows what the page actually rendered rather
    than only that a list was empty.

## B2 · Programming principles

One pattern introduced, on the backend, with its alternatives written into the
commit rather than into a document nobody reads, and one existing instance of
the same pattern extended by the week's security fix. Mobile adds no pattern
this week and none is claimed for it; what it does add is an extraction,
reported below as what it is.

### Template Method

**The practical problem.** Four profile fields (`nama`, `no_hp`,
`jenis_kelamin`, `tanggal_lahir`) have the same rules wherever a profile is
written, but all four validators were **copied whole** into two serializers,
message strings included.

**The copies had already drifted, and that is how the ticket's bug was found.**
The missing null check was present in both copies, because both had been
rewritten from memory, and a third serializer behind the nasabah's own profile
endpoint had **no birth-date rule at all**, so a nasabah could save a year-2999
birth date on their own profile while the pengurus path rejected it. One rule
copied three times is three chances to differ.

**What the pattern does.** `ProfilFieldRules` holds the invariant part: the
order of the checks for each field and the wording of each message. The
subclasses supply only the step that genuinely differs between models,
`allowed_genders`, because `Nasabah.Gender` and `User.Gender` are two separate
enums with the same contents, and `shared_kernel` must not import a model to
pick one.

**What it buys, concretely.** The mixin is installed in front of
`ModelSerializer` so DRF still finds the `validate_*` methods through the
method resolution order, and a serializer remains free to override a single
rule when it genuinely needs to.

| Considered | Verdict |
|---|---|
| One free function per rule, called from each `validate_*` | **Rejected.** That is what `tanggal_lahir_valid` already does, and it only moves the body: every serializer still has to remember to write all four wrappers, which is precisely the omission that left the hole in the account-profile path. |
| A full base class rather than a mixin | **Rejected.** The three serializers have different `Meta` classes and different derived fields, so a base class forces wider inheritance than four rules need. |
| Field-level validators on each declared field | **Rejected.** It moves the rule into the declaration, but each serializer still redeclares its fields, and the nama rule also strips whitespace, which has to run before the length check. |

One serializer is **deliberately left out of the mixin**, and the reason is a
distinction worth keeping: the account-profile path checks only two fields, so
installing the mixin there would also add the nama and gender checks it never
had. That is a tightening of behaviour rather than a refactor, so it belongs in
a commit of its own.

Arrives in
[`b8c48bf6`](https://github.com/bank-sampah-PILAH/pilah-be/commit/b8c48bf6),
with no behaviour change, stated checkably: **1004 tests with exactly the same
result as before the commit, and not one test file adjusted.**

### Enforcing an abstract member without an abstract base class

From the review round, and worth keeping because it is reusable. The abstract
member started as a method body that raised `NotImplementedError`, which fails
**at request time**, and only on a request that happens to carry a gender. A
serializer that forgot to define it would pass import and pass every test that
did not touch the field.

`abc.ABC` is not available here: `ModelSerializer` already carries
`SerializerMetaclass`, and adding `ABCMeta` beside it is a metaclass conflict.
`__init_subclass__` gives the same import-time failure without touching the
metaclass:

```python
def __init_subclass__(cls, **kwargs: object) -> None:
    super().__init_subclass__(**kwargs)
    if cls.allowed_genders is ProfilFieldRules.allowed_genders:
        raise TypeError(...)
```

The identity check is what lets an intermediate base define the member for its
own subclasses, which a test proves rather than a comment asserts. Arrives in
[`a6d34360`](https://github.com/bank-sampah-PILAH/pilah-be/commit/a6d34360).

### On mobile: an extraction, not a pattern

`OnboardingBirthDateField` is lifted out of a `build()` method that had reached
cognitive complexity 20 against a limit of 15. One `isOptional` flag then drives
the asterisk, the hint, the clear button and the validator **together**, so the
four cannot contradict each other, which is exactly the defect the review had
found: the screen said "Semua kolom bertanda * wajib diisi." while the field's
own hint read "dd/mm/yyyy (opsional)", and the asterisk asserted the opposite of
the ticket's goal.

That is single responsibility and a removed Sonar issue. It is not a GoF
pattern, and calling it one to reach a second case would be padding.

The accompanying change is small and easy to miss: the field's `Semantics` label
became `'<label>, wajib diisi'` or `'<label>, opsional'`, so a screen reader
learns what the asterisk shows. It was safe to change because no existing test
looked an onboarding field up by its semantics label, which was checked rather
than assumed.

### Template Method again, in a template rather than in a class

**Not a new pattern on this page, and saying so is the point.** be #174's
change lands inside an instance of the same pattern PIL-478 introduces above,
one `staging` already had, and it is reported as an extension of that instance
rather than as a second case.

`api/templates/swagger_ui_bernonce.html` is
`{% extends "drf_spectacular/swagger_ui.html" %}`. Upstream's template fixes
the skeleton of the page; this copy overrides named steps in it. The `head`
block was already overridden, by the CSP work in
[Sprint 2 · Week 3](s2-w3.md#b6-security), to put a nonce on upstream's
inline `<style>`. This pull request overrides the **`body`** block as well,
because that is where upstream keeps the two script tags that needed hashes.
`SwaggerUIView.get` is the same shape one level up:
`SpectacularSwaggerSplitView` runs the request and the override only adds keys
to its response data, `csp_nonce` before and now `sri`.

**The discipline the pattern asks for is visible in what was deliberately not
overridden:**

- The `{% if script_url %}` branch inside the `body` block is copied
  **unchanged**. `SpectacularSwaggerSplitView` exists precisely so the init
  script is served as a separate file rather than an inline tag, which is what
  the strict policy needs. Overriding a step means preserving the step's
  contract, not improving it on the way past.
- The template holds **no hash of its own**; all three come from
  `settings.SWAGGER_UI_SRI` through the view.
- Everything else stays upstream's, so a drf-spectacular upgrade keeps
  arriving. The cost of the two copied blocks is written into the template's
  own comment: an upstream change to `head` or `body` is silently lost, and the
  two tests named there are what make that loss visible rather than invisible.

!!! note "What is not a pattern here, and is not labelled as one"
    The version-keyed hash lookup below is a registry, which is not in the
    catalogue, and it is reported as a fail-closed principle instead of being
    dressed as Strategy or Factory to raise a count. This site has had to
    correct exactly that kind of mislabelling once already, on
    [Sprint 1 · Week 3](s1-w3.md), and a grader who knows the catalogue knocks
    down a wrong name faster than a missing one.

### Fail closed: keying the hashes by the version they came from

On be #174, and the better half of that pull request. The three sha384 hashes
started as a flat dict beside `SWAGGER_UI_VERSION`, with a comment asking
whoever bumps the version to recompute them. **A comment enforces nothing**,
and the failure mode is unpleasant: every test still passes, `manage.py check`
is clean, and the only symptom is a browser silently refusing three files, so
the docs page is blank for the next developer who opens it. An integrity
control that can quietly become decorative is worse than none, because it also
buys false confidence.

The hashes now live **under** the version they were computed from and are
looked up by it:

```python
_SWAGGER_UI_SRI_BY_VERSION = {
    "5.35.0": {"css": "sha384-...", "bundle": "sha384-...", "standalone": "sha384-..."},
}
SWAGGER_UI_SRI = _SWAGGER_UI_SRI_BY_VERSION[SWAGGER_UI_VERSION]
```

A version bump without its entry is now a `KeyError` **at settings import**,
which means in `manage.py`, in CI and in every single test, rather than a blank
page in somebody's browser. Verified rather than asserted: setting the version
to `5.36.0` with no entry makes `manage.py check` die with
`KeyError: '5.36.0'`. The principle is fail-closed, with one source of truth
for the pair, and the template holds no hash of its own.

| Considered | Verdict |
|---|---|
| Keep the flat dict, keep the comment | **Rejected.** That is what the review found. Nothing executes a comment, and the mistake it warns about is invisible to the whole suite. |
| Write the hashes into the template beside the tags | **Rejected.** The version then lives in `settings` and its hashes in a template, which is two files to keep in step and the second is not where anyone looks when bumping a dependency. |
| Add a test asserting the dict has an entry for the current version | **Rejected, and this is the interesting one.** Settings import on every test run already **is** that assertion, so the test would only restate it in a place that can drift. No test was added on purpose, and that reasoning is written in the review thread rather than left implied. |

Arrives in
[`c70c5dc8`](https://github.com/bank-sampah-PILAH/pilah-be/commit/c70c5dc8),
with no behaviour change at 5.35.0: the same three values, the same bytes
served.

All three are conventional commits on a `staging` base, and be #174's are the
clearest example on this page of commit bodies carrying the reasoning: each red
says what is missing and why that order is forced, each green names the OWASP
item, and the refactor names the reviewer who raised it.

=== "The merge order was a constraint, not a preference"

    Mobile sends an explicit `"tanggal_lahir": null`, and `staging`'s
    validators compared before checking for null. Landing mobile first would
    have meant that saving a nasabah without a birth date returned a **500 in
    production**. Both reviewers independently reached the same conclusion and
    stated it in their reviews, and the backend merged 16 minutes before the
    mobile half.

    This is the kind of dependency that is invisible in either diff on its own,
    which is why both pull-request bodies name the other half and why the
    backend's own body documents the wire contract it is the far end of.

=== "A cherry-pick rather than a rebase"

    The backend's CI was red for two days on a single failing test, and it was
    never this pull request's fault. The job is only *named* "Verify (lint,
    tests, migrations, checks, types)": the lint, format, dependency and both
    migration steps all passed, and the one failure was a shared reporting test
    whose rolling window no longer contained its own fixture rows once the real
    clock moved past them.

    The fix existed on three sibling branches. It was brought over as a
    **cherry-pick** of the single commit rather than by rebasing onto one of
    those branches, which would have dragged unrelated ledger and export
    changes into this diff. The reviewer had identified the same commit and
    checked that its parent was this branch's merge base, so it would apply
    cleanly.

    The part worth remembering is what the red run was hiding. A failed test
    step **aborts the job**, so mypy strict, the coverage gate and the Sonar

=== "backend 175, Vegard, a 422 for a malformed nasabah_id (PIL-482)"

    A `nasabah_id` filter that arrived malformed used to 500. The fix extracts
    a `validasi_uuid` helper into `shared_kernel` and answers 422 instead,
    which also rewrites the same filter inside two ledger queries.

    **The positive point is a mutation check rather than a reading.** I removed

    one side of the ledger, and that is a statement about the suite rather than
    an opinion about the diff. It is also the part the existing approval did
    not cover.

    **The finding: `kunci` is the one part of the new helper that nothing
    exercises.** All three callsites pass `kunci="nasabah_id"`, and
    `tests/test_nasabah_id_http.py` asserts that same key, so a `validasi_uuid`
    that ignored the parameter and hardcoded `{"nasabah_id": exc.detail}` would
    pass the whole suite. That parameter is the reason the helper is worth
    extracting at all, and it is the line the next caller will break.

    **The fix is sized to be takeable in the same pull request.**
    `shared_kernel/pencarian.py`, the module this helper is modelled on, has
    `shared_kernel/test_pencarian.py` beside it. A
    `shared_kernel/test_parameter.py` closes the gap in about ten lines: one
    case asserting that a different `kunci` comes back as the error key, and
    one asserting the return value is a `UUID` instance rather than the string
    that went in, which is what the annotation promises.

=== "backend 176, Vegard, waste categories read through tercatat()"

    The waste-category report stopped spelling out its own status filter and
    reads counted setoran through the `tercatat()` queryset instead, with a
    fitness test to keep it that way.

    **The positive point, and one consequence worth naming.** The rewrite lands
    on the idiom the file already uses:
    `DetailTransaksi.objects.filter(transaksi__in=...)` over a `tercatat()`
    queryset is what `DashboardService.stats` does at
    `apps/reporting/services.py:28`, so reporting now reads the same way from
    top to bottom. The fitness test also fails on exactly one line on
    `staging`, which is good evidence that it is not vacuous, and writing a
    fitness test that can actually fail is the hard part of having one. That is
    worth saying on this page in particular, because a test that cannot fail is
    exactly the defect [B1](#the-vacuous-test-which-is-the-strongest-b1-item-this-week)
    reports above.

    **The finding: the selection around the rule is now duplicated.** `counted`
    at `apps/reporting/services.py:96` is the same queryset
    `operational_trends` builds at `:62`:

    ```python
    Transaksi.objects.tercatat().filter(
        bank_sampah=bank, tipe=Transaksi.Tipe.SETORAN, tanggal__range=(start_dt, end_dt)
    )
    ```

    The new test guards the spelling of the **status**, but not the selection
    wrapped around it. So "counted setoran for this bank in this range" is now
    written twice in one class, the third reader will copy it again, and if
    what counts changes, another `tipe` or a different date bound, it has to
    change in both places with no guard saying so.

    **The fix keeps the win and drops the copy.** A module-level helper in the
    same file:

    ```python
    def _setoran_tercatat(bank: BankSampah, start_dt: datetime, end_dt: datetime) -> TransaksiQuerySet:
        return Transaksi.objects.tercatat().filter(
            bank_sampah=bank,
            tipe=Transaksi.Tipe.SETORAN,
            tanggal__range=(start_dt, end_dt),
        )
    ```

    `operational_trends` keeps its `.annotate(...)` chain on top of it and
    `waste_categories` uses it directly. The suggestion names the two imports
    that have to join the existing `api.models` line, `BankSampah` and
    `TransaksiQuerySet`, so it stays clean under mypy strict, and it says which
    caller to **leave alone**: `stats` is the same queryset minus `tipe`, and
    parameterising the helper to absorb it would trade one duplication for one
    flag.

## B6 · Security

**A08, software and data integrity failures, named in all five commit bodies on
be #174, and fixed in code.** PIL-478 names no item on either half, and none is
claimed for it; a birth date that may be absent does not touch who can reach
what, what is stored, or what is rendered from input.

### What the alert was, and what the fix does

The authenticated ZAP scan of 16 November, run against a local copy of
`staging`, reported **Sub Resource Integrity Attribute Missing**, Medium, with
**three instances**, plus **two Low** *Cross-Domain JavaScript Source File
Inclusion* instances on the same tags. All five were the API documentation
page loading Swagger UI from `cdn.jsdelivr.net`.

The shape of the problem, stated as the commit bodies state it: an unpinned
CDN URL is **an immutable-looking reference to mutable content**. Those scripts
run with the page's own privileges, so whoever controls what that URL returns
controls the page. Two things were therefore wrong, and they had to be fixed in
this order:

1. **The reference moved.** `swagger-ui-dist@latest` is drf-spectacular's
   default, and its contents change without notice. Pinned to 5.35.0, which is
   what `@latest` resolved to that day, so the page serves the same bytes it
   served before the pin.
2. **Nothing verified what arrived.** The three executable subresources now
   carry `integrity="sha384-..."` and `crossorigin="anonymous"`, computed
   against the bytes jsdelivr serves for 5.35.0, so the browser refuses
   anything else outright.

**The scope is stated in the commit body rather than left flattering.**
`SwaggerUIView` is `debug_only`, so `/api/docs/` answers 404 in production and
the reach of this fix is development machines. It is still a real alert on a
real page, and the CDN is still a third party we do not control, but it is not
a production exposure and is not written up as one.

## B2 · Programming principles

### Template Method

**The practical problem.** Four profile fields (`nama`, `no_hp`,
`jenis_kelamin`, `tanggal_lahir`) have the same rules wherever a profile is
written, but all four validators were **copied whole** into two serializers,
message strings included.

**The copies had already drifted, and that is how the ticket's bug was found.**
The missing null check was present in both copies, because both had been
rewritten from memory, and a third serializer behind the nasabah's own profile
endpoint had **no birth-date rule at all**, so a nasabah could save a year-2999
birth date on their own profile while the pengurus path rejected it. One rule
copied three times is three chances to differ.

**What the pattern does.** `ProfilFieldRules` holds the invariant part: the
order of the checks for each field and the wording of each message. The
subclasses supply only the step that genuinely differs between models,
`allowed_genders`, because `Nasabah.Gender` and `User.Gender` are two separate
enums with the same contents, and `shared_kernel` must not import a model to
pick one.

**What it buys, concretely.** The mixin is installed in front of
`ModelSerializer` so DRF still finds the `validate_*` methods through the
method resolution order, and a serializer remains free to override a single
rule when it genuinely needs to.

| Considered | Verdict |
|---|---|
| One free function per rule, called from each `validate_*` | **Rejected.** That is what `tanggal_lahir_valid` already does, and it only moves the body: every serializer still has to remember to write all four wrappers, which is precisely the omission that left the hole in the account-profile path. |
| A full base class rather than a mixin | **Rejected.** The three serializers have different `Meta` classes and different derived fields, so a base class forces wider inheritance than four rules need. |
| Field-level validators on each declared field | **Rejected.** It moves the rule into the declaration, but each serializer still redeclares its fields, and the nama rule also strips whitespace, which has to run before the length check. |

One serializer is **deliberately left out of the mixin**, and the reason is a
distinction worth keeping: the account-profile path checks only two fields, so
installing the mixin there would also add the nama and gender checks it never
had. That is a tightening of behaviour rather than a refactor, so it belongs in
a commit of its own.

Arrives in
[`b8c48bf6`](https://github.com/bank-sampah-PILAH/pilah-be/commit/b8c48bf6),
with no behaviour change, stated checkably: **1004 tests with exactly the same
result as before the commit, and not one test file adjusted.**

### Enforcing an abstract member without an abstract base class

From the review round, and worth keeping because it is reusable. The abstract
member started as a method body that raised `NotImplementedError`, which fails
**at request time**, and only on a request that happens to carry a gender. A
serializer that forgot to define it would pass import and pass every test that
did not touch the field.

`abc.ABC` is not available here: `ModelSerializer` already carries
`SerializerMetaclass`, and adding `ABCMeta` beside it is a metaclass conflict.
`__init_subclass__` gives the same import-time failure without touching the
metaclass:

```python
def __init_subclass__(cls, **kwargs: object) -> None:
    super().__init_subclass__(**kwargs)
    if cls.allowed_genders is ProfilFieldRules.allowed_genders:
        raise TypeError(...)
```

The identity check is what lets an intermediate base define the member for its
own subclasses, which a test proves rather than a comment asserts. Arrives in
[`a6d34360`](https://github.com/bank-sampah-PILAH/pilah-be/commit/a6d34360).

### On mobile: an extraction, not a pattern

`OnboardingBirthDateField` is lifted out of a `build()` method that had reached
cognitive complexity 20 against a limit of 15. One `isOptional` flag then drives
the asterisk, the hint, the clear button and the validator **together**, so the
four cannot contradict each other, which is exactly the defect the review had
found: the screen said "Semua kolom bertanda * wajib diisi." while the field's
own hint read "dd/mm/yyyy (opsional)", and the asterisk asserted the opposite of
the ticket's goal.

That is single responsibility and a removed Sonar issue. It is not a GoF
pattern, and calling it one to reach a second case would be padding.

The accompanying change is small and easy to miss: the field's `Semantics` label
became `'<label>, wajib diisi'` or `'<label>, opsional'`, so a screen reader
learns what the asterisk shows. It was safe to change because no existing test
looked an onboarding field up by its semantics label, which was checked rather
than assumed.

=== "The merge order was a constraint, not a preference"

    Mobile sends an explicit `"tanggal_lahir": null`, and `staging`'s

    have meant that saving a nasabah without a birth date returned a **500 in
    production**. Both reviewers independently reached the same conclusion and
    stated it in their reviews, and the backend merged 16 minutes before the
    mobile half.

    This is the kind of dependency that is invisible in either diff on its own,
    which is why both pull-request bodies name the other half and why the
    backend's own body documents the wire contract it is the far end of.

=== "A cherry-pick rather than a rebase"

    The backend's CI was red for two days on a single failing test, and it was
    never this pull request's fault. The job is only *named* "Verify (lint,
    tests, migrations, checks, types)": the lint, format, dependency and both
    migration steps all passed, and the one failure was a shared reporting test
    whose rolling window no longer contained its own fixture rows once the real
    clock moved past them.

    The fix existed on three sibling branches. It was brought over as a
    **cherry-pick** of the single commit rather than by rebasing onto one of
    those branches, which would have dragged unrelated ledger and export
    changes into this diff. The reviewer had identified the same commit and
    checked that its parent was this branch's merge base, so it would apply
    cleanly.

    The part worth remembering is what the red run was hiding. A failed test
    step **aborts the job**, so mypy strict, the coverage gate and the Sonar
    analysis had not failed, they had never run. The first green run was
    therefore the first time any of those three reported anything at all, which
    is why no quality figure existed for this pull request until two days
    before it merged.

=== "The merge itself was taken out of my hands"

    A hold was in force. The decision was to wait until the next morning
    before merging anything, even though both pull requests were green,
    approved and mergeable. Overnight a teammate merged both.

    Nothing was lost by it, the order was still correct, and the hold had been
    about confirming the sprint boundary rather than about the code. It is
    recorded because it is the reason the last review on the mobile half was
    never answered, which is in

### Test doubles: all three levels of the rule, in one week

The [standing rule](../part-b.md#the-rule-for-test-doubles) is no double when
there are no collaborators, a stub by default and as low as possible, and a
mock only when there is no observable result. This week happens to contain one
clean example of each, so it is worth showing them together.

=== "No double at all — mobile #186"

    `side_sheet_page_test.dart` is 27 widget cases and its entire import list
    is Flutter plus the file under test:

    ```dart
    import 'package:flutter/material.dart';
    import 'package:flutter/services.dart';
    import 'package:flutter_test/flutter_test.dart';
    import 'package:pilah_mobile/design/layout/side_sheet_presentation.dart';
    ```

    No stub, no mock, no support helper. That is **rule 1, not an oversight**:
    a side sheet container has no collaborators. It takes a widget, puts it in
    a route, and decides whether a pop may proceed. Everything it does is
    observable from the widget tree.

    This is the pay-off from the Factory Method choice in
    [B2](#b2-programming-principles). Because the panel is a plain framework
    `Page` rather than a go_router one, the test does not need a router, and
    because it needs no router it needs nothing faked. A container that had
    reached for go_router directly would have forced a double into every one
    of those 27 cases.

    The one collaborator that does exist is injected rather than faked:
    `SideSheetGuard` takes `hasUnsavedInput` as a `bool Function()`, so a test
    hands it `() => true`. That is a parameter, not a test double.

=== "A stub at the transport boundary — mobile #195"

    The setoran form has real collaborators: harga, profile, nasabah and
    transaksi all load over HTTP. `StubApi` fakes **the HTTP boundary and
    nothing above it** — its own comment calls a recorded entry "one request
    that reached the HTTP boundary". Every provider, notifier, repository and
    serialiser above it is the real one.

    ```dart
    api.on('GET', '/api/v1/jenis-sampah', json: {'results': [], 'next': null});
    api.on('GET', '/api/v1/nasabah',      json: {'results': [], 'next': null});
    api.on('GET', '/api/v1/dashboard/stats', json: <String, dynamic>{});
    ```

    This is rule 2 — fake the socket, keep the app — and the reason it matters
    here is specific. These tests are about **where the form appears**, not
    what it loads, so `test/support/setoran_form_support.dart` says so in its
    own words: *"Quiet stubs only: every endpoint answers empty, because none
    of these tests is about what the form loads."* A double that answered with
    realistic fixtures would invite assertions about content into tests whose
    subject is layout.

    The helper exists because of the change itself. Previously the form was
    reachable only as its own route, so a test about the navigation rail could
    register a placeholder page and never build the real form. Opening it
    inline means tapping "Tambah Transaksi" now renders the genuine form, so
    tests that are about the *menu* suddenly need the form's providers. That
    is a real cost of the feature, and it is paid once in a shared helper
    rather than copied into each suite.

    !!! note "A red error block inside a passing test is expected here"
        The side-sheet suite deliberately stubs a 404 on one path, so the run
        prints a `NotFoundException` / `DioException` stack in the middle of a
        green suite. It is the double doing its job. Worth knowing before
        someone reads the log and reports a failure that is not one.

=== "A mock, where nothing is observable — the shared harness"

    `StubApi` also carries the one genuine mock:

    ```dart
    class _MockSecureDatabase extends Mock implements SecureDatabase {}
    ```

    Secure storage is rule 3's exact case: writing a token to the platform
    keystore produces **no observable result** a test can read back. There is
    no state to assert on and no response to inspect, so the only thing left
    to verify is that the call was made — which is what a mock is for and what
    a stub cannot do.

    Alongside it sits `StubEnvironment`, a fixed fake `.env`, so no test ever
    reads real configuration off the machine it happens to run on.

=== "Unchanged, and that is the point — mobile #202"

    The Pengumuman removal adds no new doubles. Its tests reuse the same
    `StubApi`, and the route-lockout cases need three quiet stubs for one
    reason worth stating: the redirect lands on the dashboard, so the
    dashboard's own fetches have to answer something.

    ```dart
    api.on('GET', '/api/v1/dashboard/stats', json: <String, dynamic>{});
    api.on('GET', '/api/v1/transaksi', json: {'results': []});
    api.on('GET', '/api/v1/pencairan', json: {'count': 0, 'next': null, 'results': []});
    ```

    Those three stubs are a consequence of the design decision in
    [B6](#b6-security) — redirecting rather than deleting — showing up in the
    test setup. A deletion would have needed no stubs and would also have
    shown the user an error page.

    One double was **deleted**: `test/support/beranda_pengumuman_support.dart`
    went with the feature's entry points. A support file nobody uses is a
    maintenance cost that looks like coverage.

## B2 · Programming principles

Three design patterns, each in its own commit so the diff is linkable. Factory
Method and Template Method arrive in **#186**, Strategy in **#195**; **#202**
has none and none is claimed for it.

Each is here because a specific thing would otherwise have gone wrong. The
pattern name is the last thing that matters about it, so the plain problem
comes first.

### Factory Method

**The practical problem.** The design system has to hand the app a panel. Only
the app knows which routing package is in play. If `lib/design/` imported
go_router to build that panel, the entire design system would be welded to one
router, and every test of the panel would have to boot a router before it could
check a width.

**What the pattern does.** `SideSheetPage` is a plain Flutter `Page`, and
`Page` already has exactly one job: *when the time comes, make me a route*. The
method is `createRoute`. Overriding that one method is the whole pattern — the
framework asks, our subclass answers with `_SideSheetRoute`, and nobody holding
the page ever names a route type.

**What it buys, concretely.** `lib/design/` imports nothing from go_router. The
same object works in go_router's declarative page list **and** under a bare
`Navigator.push`. And the panel's 27 widget tests build it with no router at
all, which is why they are fast and why they test the panel rather than the
routing.

| Considered | Verdict |
|---|---|
| go_router's `CustomTransitionPage` | **Rejected.** Fewer lines, same result, and it binds `lib/design/` to go_router. A design-system primitive that works under only one router is not a primitive. |
| `showGeneralDialog` on the root navigator | **Rejected, after being chosen first.** It was the original container. A dialog opened straight onto the navigator never enters go_router's page list, so it creates no browser history entry — and the browser's back button then reached past the panel and popped the page underneath, taking the unsaved form with it. |

Arrives in
[`7655eacc`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/7655eacc).

### Template Method

**The practical problem.** A panel needs a scrim, a slide-in from the right,
Esc and back handling, and one thing more important than all of those: it must
not erase the page behind it. Building that by hand means re-implementing
Flutter's modal machinery, and the part that is easy to get wrong is the pop
lifecycle, which is also the part that loses someone's half-typed setoran.

**What the pattern does.** `PageRoute` already owns the algorithm — install,
animate in, hold the barrier, pop, animate out — and leaves blanks for the
parts that differ per route. `_SideSheetRoute` fills in the blanks and inherits
the rest.

**What it buys, concretely.** The ticket's real requirement turns out to be
*one blank*:

```dart
@override
bool get opaque => false;
```

An opaque route lets Flutter stop painting, and eventually unmount, whatever is
underneath. That one line is what keeps the dashboard alive and visible behind
the panel, which is the entire point of PIL-432. Everything else — the barrier,
the pop lifecycle, the transition plumbing — came for free and is the part most
likely to have been wrong if hand-rolled.

| Considered | Verdict |
|---|---|
| A persistent `Overlay` entry plus shared state | **Rejected.** Closest to Material's own non-modal side sheet, but an overlay is not a route: no back-button integration, and a page left interactive behind a live form can navigate away mid-submit. |

### Strategy

**The practical problem.** One setoran form now runs in two places, and "close
me" means three different things depending on where it is and what just
happened. Worse, the obvious call is a trap: `GoRouter.pop()` from inside the
panel pops the **page behind** the panel, because the panel is pushed onto the
navigator rather than matched by the router. A form that decides its own exit
has to know which container it is in, and gets one case wrong.

**What the pattern does.** The form takes *how to close* as a parameter. Each
container passes its own:

| Container | The `onClose` it injects | Why that one |
|---|---|---|
| `TransaksiBaruPage`, full screen | `context.pop()` | go_router owns the page, so popping it is correct. |
| The panel's header close button | `Navigator.of(sheetContext).maybePop()` | `maybePop` is the only pop that consults `PopScope`, so this exit runs the unsaved-input question. A close button is an exit people hit by accident. |
| The panel, after a successful save | `allowNextExit()` then `Navigator.of(sheetContext).pop()` | The user already decided. Asking again would hold up the save they just requested. |

**What it buys, concretely.** The form knows about none of the three, so the
dangerous call is not available to it. A third container would need no change
to the form at all. And the form became testable on its own, because it no
longer needs a route to close.

| Considered | Verdict |
|---|---|
| A container `enum` on the form plus a branch at each exit | **Rejected.** It puts the container's knowledge back inside the content, and the widget could then be tested only through its containers. |

The extraction is a `refactor` commit separate from everything that uses it,
and its claim to change no behaviour is checkable rather than asserted:
**423 existing tests stayed green with zero test edits.** Commits
[`d248292c`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/d248292c)
and
[`0b3dd860`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/0b3dd860).

!!! note "One object here is deliberately given no pattern name"
    `SideSheetGuard` holds a one-shot latch and is shared by two exit paths
    that do not know about each other — `PopScope`, which only
    `Navigator.maybePop` consults, and `GoRoute.onExit`, which is the only hook
    a browser history traversal passes through. One object, because two would
    ask the user twice about a single close.

    It is the most interesting thing on the branch and it is not a GoF pattern.
    Calling it a Mediator because it sits between two collaborators would be
    padding the count, and the criterion asks for *different cases*, not for
    more labels.

    PIL-436 (#202) adds no pattern either. The one piece of structure it does
    add — the four locked URLs derived by looping one exported route list
    rather than retyped beside it — is a single source of truth, which is a
    principle. Calling it a pattern would be reaching.

## The defect, which was not the one I expected

`POST /api/v1/transaksi` carries an `Idempotency-Key` header — the mechanism
behind **BR-04**, the rule that a repeated request must not move a nasabah's
balance twice. `CORS_ALLOW_ALL_ORIGINS=true` permits any *origin* but not
arbitrary *headers*: django-cors-headers answers the preflight with its own
default list, which I confirmed by printing it rather than trusting the docs:

```python
>>> from corsheaders.defaults import default_headers
('accept', 'authorization', 'content-type', 'user-agent', 'x-csrftoken', 'x-requested-with')
```

No `idempotency-key`, and `CORS_ALLOW_HEADERS` was set nowhere in the
repository. So the browser refused to send the request, and only `OPTIONS`
reached the server.

The obvious fix is one settings line. The **actual** defect was a layer down:

!!! danger "Two literals that had to agree, with nothing checking that they did"
    [`apps/ledger/views.py`](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/apps/ledger/views.py#L64)
    read the string `"Idempotency-Key"`. `config/settings.py` would have
    spelled `"idempotency-key"` independently, in a different file, for a
    different purpose. Nothing related them.

    The missing value was the symptom. The drift was the defect — and it would
    recur for the next custom header.

**Why nobody had seen it for months:** CORS is a browser-only mechanism. The
native app sends no preflight, so the header always sailed through. Web was
simply the first client to send it. In practice BR-04's protection against a
double setoran had only ever been active on native.

### Positive, negative, corner

=== "Positive"

    [View](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/tests/regression/identity/test_cors.py#L38-L51)

    ```python
    def test_preflight_allows_the_idempotency_key_header(self) -> None:
        ...
        self.assertIn("idempotency-key", response["Access-Control-Allow-Headers"].lower())
    ```

    Red first, and the failure message named the bug by itself:

    ```
    AssertionError: 'idempotency-key' not found in 'accept, authorization,
    content-type, user-agent, x-csrftoken, x-requested-with'
    ```

    That output *is* the diagnosis — the library's default list, printed by the
    failing test. A red state that explains the cause is worth more than one
    that only says `False is not True`.

=== "Negative"

    [View](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/tests/regression/identity/test_cors.py#L96-L110)

    ```python
    def test_preflight_does_not_allow_an_unregistered_custom_header(self) -> None:
        ...
        allowed = response["Access-Control-Allow-Headers"].lower()
        self.assertNotIn("x-pilah-tidak-terdaftar", allowed)
        self.assertNotIn("*", allowed)
    ```

    The fix *loosens* CORS, so the negative case matters more than usual: it
    pins that the list stayed an allow-list and did not become a wildcard. The
    easy wrong fix for this bug is `CORS_ALLOW_HEADERS = ["*"]`, which passes
    the positive test above and quietly opens everything.

=== "Corner"

    [View](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/tests/regression/identity/test_cors.py#L73-L94)

    ```python
    def test_every_registered_custom_request_header_passes_preflight(self) -> None:
        requested = ",".join(header.lower() for header in HEADER_PERMINTAAN_KUSTOM)
        ...
        self.assertTrue(HEADER_PERMINTAAN_KUSTOM, "registry must not be empty")
        for header in HEADER_PERMINTAAN_KUSTOM:
            with self.subTest(header=header):
                self.assertIn(header.lower(), allowed)
    ```

    The corner case is not a value — it is **header number two**, which does
    not exist yet. Iterating the registry means the next custom header is
    covered before anyone writes a test for it.

    The `assertTrue` guard is there because a `for` loop over an empty tuple
    passes vacuously, which is the one way this test could quietly stop
    testing.

    A second corner case asserts **list equality**, not membership, on the
    exposed response headers
    ([view](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/tests/regression/identity/test_cors.py#L112-L127)) —
    `assertIn` would never notice an *extra* header leaking out to JavaScript.

## Test doubles: none, and that is the honest answer

The previous week's
[test-doubles section](s1-w3.md#test-doubles-what-is-faked-and-what-it-costs)
sets out three levels of faking. **This week uses none of them**, and inventing
one to satisfy a rubric would have made the tests worse.

There is no collaborator to fake. The tests drive the real django-cors-headers
middleware through the real request pipeline and read the real response
headers. That is the point: the defect lived *in the configuration of that
middleware*, so a test which faked the middleware could not have caught it.

They do use one isolation technique worth naming:

```python
with override_settings(
    CORS_ALLOW_ALL_ORIGINS=False,
    CORS_ALLOWED_ORIGINS=["http://localhost:7357"],
):
```

**Practically: a configuration stub.** It says *pretend, just for this test,
that only `localhost:7357` is an allowed origin*. Without it the assertions
would depend on whatever `CORS_ALLOW_ALL_ORIGINS` happens to be in the ambient
environment, and the suite would pass or fail according to a developer's `.env`
rather than according to the code.

**Implication.** It isolates configuration, not collaborators — so it costs
none of the coupling a mock costs, and buys none of the reach either. It cannot
tell you the middleware is wired into `MIDDLEWARE` at all; only a real request
can. Which is why the fix was also checked against a running server.

## B2 · Programming principles

**Single source of truth, as a registry.**
[`shared_kernel/http_headers.py`](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/shared_kernel/http_headers.py)
holds every custom header name once, and three places derive from it:

| Consumer | Line |
|---|---|
| the view that reads the header | [`views.py:64`](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/apps/ledger/views.py#L64) |
| `CORS_ALLOW_HEADERS` | [`settings.py:234-237`](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/config/settings.py#L234-L237) |
| `CORS_EXPOSE_HEADERS` | [`settings.py:238`](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/config/settings.py#L238) |

```python
CORS_ALLOW_HEADERS = (
    *default_headers,
    *(header.lower() for header in HEADER_PERMINTAAN_KUSTOM),
)
CORS_EXPOSE_HEADERS = HEADER_RESPONS_TEREKSPOS
```

!!! important "Why this is a Registry and not a Singleton"
    A Singleton was the obvious pattern to reach for, and I did not use it.
    **In Python a module already is a singleton** — imported once, cached in
    `sys.modules`, shared by every importer. A class with `getInstance()` would
    have added ceremony and changed nothing about the guarantee.

    The pattern that actually fixes this defect is a **Registry**: one named
    place that owns a set of values which other components read instead of
    restating. Calling it a Singleton would have been pattern cosplay — the
    accurate label matters more than the more impressive one.

**Dependency direction, deliberately.** The module imports **no Django at
all**. That is not minimalism, it is a constraint: `config/settings.py` imports
it while settings are still loading, before the app registry exists, so a
single `django.db` import anywhere in its chain would break startup. It also
keeps the modular-monolith boundary that
[`tests/test_architecture.py`](https://github.com/bank-sampah-PILAH/pilah-be/blob/02c685e/tests/test_architecture.py)
enforces — `shared_kernel` may not import `apps.*`, and this does not.

**Open/Closed, checkable.** `apps/ledger/views.py` changed by **two lines**, an
import and a lookup, and 117 tests across cors, architecture and ledger passed
unedited. Adding the next custom header means editing the registry only.

Named in the commit body, which is where the criterion asks for it:

```text
OWASP A05:2021 Security Misconfiguration. Kelemahannya bukan nilai yang
salah melainkan konfigurasi yang implisit: daftar header lintas origin
dibiarkan mengikuti bawaan pustaka padahal kontrak API sudah berbeda.
Daftar tetap berupa allow-list eksplisit, bukan wildcard.
```

The claim is deliberately narrow. **Allowing a header is loosening, not
hardening**, and presenting it otherwise would be dishonest. What qualifies as
A05 is that the cross-origin configuration was *implicit* — inherited from a
library default that knew nothing about this API's contract — and is now
explicit, derived from the code that uses it, and asserted by tests. Two
choices keep the change a tightening rather than a hole:

- the allow-list stays an enumeration, and the wildcard shortcut is tested
  against;
- exactly one response header is exposed, pinned by list equality, so the
  export filename becomes readable and nothing else becomes readable with it.

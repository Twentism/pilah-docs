## The design pattern: a status that owns its own rules

Four places knew the schedule lifecycle (`draf → diterbitkan → dibatalkan →
selesai`), and a fifth took the transition as a bare string:

- two near-identical `if (item.status == '...')` blocks inside
  `_ScheduleCard.build` decided which buttons exist;
- `_statusLabel` turned the string into a label;
- `_ScheduleStatus` turned it into colours;
- `JadwalCubit.changeStatus(String id, String action)` took the action as a raw
  string — so `'terbitkann'` would travel all the way to the repository.

The refactor,
[`60cceba1`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/60cceba1),
moves all of that onto the status itself. The widget goes back to only drawing.

!!! abstract "The pattern, and why this one"
    This is the **State** idea from the Gang of Four catalogue — behaviour that
    depends on which state an object is in belongs *with the state*, not in a
    conditional at every call site. In Dart the lightest honest form of it is an
    **enhanced enum**: each member carries its own label and its own set of
    legal actions.

    ```dart
    enum JadwalStatus {
      draf('draft'), diterbitkan('diterbitkan'),
      dibatalkan('dibatalkan'), selesai('selesai');

      Set<JadwalAction> get availableActions => switch (this) {
        JadwalStatus.draf        => const {JadwalAction.batalkan, JadwalAction.terbitkan},
        JadwalStatus.diterbitkan => const {JadwalAction.batalkan, JadwalAction.selesaikan},
        JadwalStatus.dibatalkan  => const {},
        JadwalStatus.selesai     => const {},
      };
    }
    ```

The rubric's Programming row at level 3 is not "applied a pattern" — it is
**compared several and justified the one chosen**. The commit body records that
comparison, so the choice is defensible rather than asserted:

=== "Chosen — enhanced enum"

    One type, three pure functions (label, colours, actions). The `switch` is
    **exhaustive**, so adding a status the compiler does not yet know about
    fails the build until its actions are defined. That compile-time
    completeness is the maintenance property the rubric asks about, and the
    repo already uses the shape in `NavigationForm` and `PickerPresentation`.

=== "Rejected — sealed class per state"

    The most literal State pattern: one class per status. But that is **four
    classes for behaviour that is three pure functions**, and Dart still
    demands a `switch` at the call sites, so the ceremony buys nothing here.

=== "Rejected — constant map"

    `Map<String, _StatusSpec>` is the fewest lines. But it has **no
    exhaustiveness check**: a new status compiles fine and fails at runtime as a
    null lookup. It trades the one guarantee that made the refactor worth doing.

One deliberate boundary: `changeStatus` still crosses the repository as a
string, via `action.wireValue`. The type safety lives at every call site in the
UI, but the data layer is untouched — the ripple is confined to one file
instead of spreading into the repository, its implementation, the data source
and three test files.

## The form as a panel, not a sheet

On a phone the create/edit form is a bottom sheet, and that stays exactly as it
was. In a browser window wide enough for it, the form now opens as a **panel
beside the agenda** using
[`MasterDetailLayout`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/6e24a21b/lib/design/layout/master_detail_layout.dart) —
the primitive [PIL-293](pil-293.md) shipped and nothing had used yet — so the
day being scheduled into stays visible while the form is filled in.

!!! danger "The threshold is `expanded`, and a test is why"
    My first cut opened the panel at *any* non-compact width. An existing
    test, `preserves selected recipients when editing a targeted schedule`,
    failed immediately: the default widget-test surface is 800×600, which is
    *medium*, so the form opened as a ~320px panel and its dropdowns could no
    longer be operated.

    That was not a stale test — it was a real finding about a real width. So
    the rule became `expanded` only, and two boundary tests (839 and 840px) now
    pin it. Below `expanded` the sheet is still the better container.

## Test doubles: which layer is faked

The [Sprint 1 · Week 3](../ir/b/s1-w3.md#test-doubles-what-is-faked-and-what-it-costs)
page sets out the taxonomy — a **stub answers**, a **mock remembers**, and what
matters is *which layer* you fake. PIL-339 uses two of those levels.

### Level 0 — no double, for the status logic

[`jadwal_status_test.dart`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/6e24a21b/test/features/jadwal/domain/jadwal_status_test.dart)
fakes nothing. `JadwalStatus` is pure Dart with no collaborators, so the test
hands it a status and checks the answer, the way you would check a calculator.

**Practically:** this is the lightest possible test and it cannot rot, because
there is no seam to drift. It is also why the pattern was worth extracting into
the domain in the first place — the lifecycle rules became testable **without
building a widget tree at all**, where before they were trapped inside
`_ScheduleCard.build`.

### Level 2 — a mock cubit, to confirm a side effect

The widget tests in
[`jadwal_web_layout_test.dart`](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/6e24a21b/test/features/jadwal/presentation/pages/jadwal_web_layout_test.dart)
stand a **mock** `JadwalCubit` in for the real one (`MockCubit` from
`bloc_test`).

!!! abstract "What the mock is standing in for, in the larger picture"
    The real `JadwalCubit` reaches out through a repository, a data source and
    an HTTP client to the backend. A widget test must not do that — it would be
    slow, non-deterministic, and would fail for reasons that have nothing to do
    with the widget. So the mock is a **pretend cubit**: it mimics the one thing
    the page needs from the real object — that calling `saveJadwal` returns "no
    failure" — without any of the network behind it.

    It is a **mock**, not a stub, because the test then *interrogates it*:

    ```dart
    verify(() => cubit.saveJadwal(any())).called(1);
    ```

    The page is asked to save, and afterwards the fake is asked *were you in
    fact told to save, exactly once?* That is the "remembers" half of the
    taxonomy — the answer is read off the double, not off the app.

**Implication.** Mocking the cubit is the right seam *here* because the thing
under test is the page's own behaviour — does saving close the panel, does the
× dismiss it — not the save itself, which has its own tests one layer down. The
cost of a mock is that it proves nothing about whether the real cubit is wired
in; so the panel was also exercised against a real backend (below), where a
genuine `POST` returned `201`.

## Positive, negative, corner

In plain terms, as three situations a Pengurus is actually in:

| | The question it answers | Here |
|---|---|---|
| **Positive** | Does the right thing happen when the user does the normal thing? | A published schedule shows exactly *Batalkan* and *Tandai Selesai* |
| **Negative** | Does the system correctly *refuse* when it should? | A browser one pixel too narrow does **not** open the panel |
| **Corner** | Does it survive the weird edge the user rarely reaches? | Stepping a month from 31 January lands on 28 February, not 3 March |

A suite with only positive cases passes while cancelled schedules show broken
buttons and 31 January rolls the calendar into March — which is why all three
are here.

=== "Positive"

    **In plain terms:** the Pengurus has already *published* a schedule and
    looks at its card. The two buttons it offers must be exactly the two things
    you are allowed to do to a live schedule — cancel it, or mark it complete.
    You cannot publish it again; it is already published.

    [View](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/6e24a21b/test/features/jadwal/domain/jadwal_status_test.dart)

    ```dart
    test('a published schedule can be cancelled or completed', () {
      expect(
        JadwalStatus.diterbitkan.availableActions,
        {JadwalAction.batalkan, JadwalAction.selesaikan},
        reason: 'it can no longer be published a second time',
      );
    });
    ```

    Asserted as **set equality**, not `contains`. Equality means the test also
    says what is *absent* — republishing a published schedule is not a legal
    action — for free. A `contains` check would have been the vacuous assertion
    a reviewer caught on the backend two weeks earlier.

=== "Negative"

    **In plain terms:** the Pengurus shrinks the browser to 839px — a small
    laptop, or a half-screen window. The form must *not* open as the side panel
    here: a panel that narrow (~320px) is too cramped to fill in, so it falls
    back to the bottom sheet. This is the feature correctly saying "no" to the
    fancy layout when the window cannot carry it.

    [View](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/6e24a21b/test/features/jadwal/presentation/pages/jadwal_web_layout_test.dart)

    ```dart
    testWidgets('one pixel below expanded the form stays a sheet', (tester) async {
      await _pumpAt(tester, const Size(839, 900));
      await tester.tap(find.byTooltip('Buat Jadwal'));
      await tester.pumpAndSettle();
      expect(find.byType(BottomSheet), findsOneWidget,
        reason: 'a 2/5 panel at medium is about 320px, too narrow for this form');
    });
    ```

    The legal-but-"no" case: at 839px the answer is *not a panel*. It guards the
    exact regression the recipients test exposed. (A cancelled schedule, which
    offers *no* buttons at all, is the same idea on the status side — the system
    correctly offering nothing.)

=== "Corner"

    **In plain terms:** the Pengurus is viewing 31 January and taps "next
    month". February has no 31st, so the app has to land on 28 February — not
    silently roll over to 3 March, which is what a raw date calculation does.
    It is the kind of boundary almost nobody thinks to test, because only four
    months of the year even have a 31st to trip on.

    [View](https://github.com/bank-sampah-PILAH/pilah-mobile/blob/6e24a21b/test/features/jadwal/presentation/pages/jadwal_web_layout_test.dart)

    ```dart
    testWidgets('navigating a month clamps to the last day of a shorter month',
        (tester) async {
      await _pumpAt(tester, const Size(1440, 900), initialDate: DateTime(2026, 1, 31));
      await tester.tap(find.byKey(const ValueKey('jadwal-calendar-toggle')));
      await tester.tap(find.byIcon(Icons.chevron_right));
      expect(find.textContaining('28 Februari'), findsWidgets,
        reason: 'without the clamp DateTime(2026, 2, 31) rolls over to 3 Maret');
    });
    ```

    Without the clamp, `DateTime(2026, 2, 31)` silently rolls over to 3 March.
    A second corner, in the status tests, is the status this build has **never
    heard of**: when the backend ships a new status like `ditunda` before the
    app is updated, `fromWire('ditunda')` must return `null` and the card must
    render with no buttons — degrade, not crash.

## The coverage report was hiding a bug

SonarCloud reported **90.91%** on the PR's new lines — six uncovered. Chasing
them turned up a defect, not a test gap. `_closePanel` had zero coverage
because **nothing could call it**:

!!! danger "The panel's close button did nothing"
    `BottomSheetHeader` dismisses itself with `context.pop()`. That is correct
    for a bottom sheet — a sheet *is* a route. But the panel sits inline in the
    page body, on no route of its own. So tapping its × called `go_router`'s
    `pop` and closed nothing; the form stayed open.

    My own Playwright pass had missed it, because I only ever closed the panel
    by *saving*. The coverage number found what manual QA did not.

The fix,
[`a20de792`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/a20de792):
`BottomSheetHeader` takes an optional `onClose`, defaulting to `context.pop()`
so every existing sheet and dialog is untouched, and only the panel supplies its
own way out. A red test
([`f68f42b5`](https://github.com/bank-sampah-PILAH/pilah-mobile/commit/f68f42b5))
showed `GoRouterHelper.pop` firing with the form still present; green made it
close.

## Verified against a real backend

The pattern is not only unit-tested — it was exercised end to end in a browser,
against a seeded `pilah-be` on `origin/staging`, driven by Playwright:

```console
POST //api/v1/jadwal                        => 201 Created
POST //api/v1/jadwal/<id>/terbitkan         => 200 OK
```

On screen the chip moved **Draf → Diterbitkan** and its buttons changed from
`Batalkan + Terbitkan` to `Batalkan + Tandai Selesai` — the UI being driven by
`availableActions`, live. Screenshots at 1440×900 and 390×844 are stored under
`artifacts/pr-113/`.

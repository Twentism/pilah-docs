## The problem

The Pengurus app had exactly one navigation form: a bottom navigation bar.
That is correct on a phone. On a 1440px monitor it puts the primary navigation
as far from the user's attention as the screen allows, and leaves content
stretched across the full width with no reading bound.

## The shape of the solution

Three window-width classes, taken from Material 3's window size classes —
because that is precisely where `NavigationBar` and `NavigationRail` are
designed to swap.

| Class | Width | Navigation | Content |
|---|---|---|---|
| compact | `< 600` | bottom bar (unchanged) | full width |
| medium | `600–839` | rail, icons only | full width |
| expanded | `>= 840` | rail, labelled + bank name | capped at 1200, centred |

The boundary belongs to the wider block: exactly 600 is medium, exactly 840 is
expanded. That is not a comment — it is pinned by on-point tests.

## The design decision I am most confident about

I extracted `RoleDestinations` **before** adding the rail, as its own
red-green pair, and left `RoleNavigationBar`'s render path byte-for-byte
unchanged.

That ordering is the whole point. The bottom bar is the form that already works
for every member on a phone; adding a second form should not be able to
disturb it. Afterwards, *which* destinations a role has is decided in exactly
one place, and *how* they are drawn belongs to each widget — Single
Responsibility, and Open/Closed in the sense that matters here: the rail was
added without modifying the bar.

It is also the security argument. Two navigation surfaces reading two lists
could drift, and the drift would be a role seeing a destination it should not.
One source makes that impossible by construction. See
[Security](../process/security.md).

## Input Space Partitioning

Window width is a continuous input, so I partitioned it and tested the
boundaries rather than picking sample widths.

| Partition | On-point | Off-point |
|---|---|---|
| compact | 599 | 600 |
| medium | 600, 839 | 599, 840 |
| expanded | 840 | 839 |

Plus degenerate input: a non-positive width returns compact rather than
throwing, because the first frame can run before the window size is known and
callers should not each have to guard that.

## Three judgement calls to defend

**No grid primitive.** The dashboard stat cards are already a fixed 3-across
`Row` with `IntrinsicHeight`. Their actual desktop problem was unbounded
width, and `ContentBounds` solved that. A grid would have been an abstraction
with no caller.

**Zero `MasterDetailLayout` call sites.** Sixteen screens still open details
as modal bottom sheets, and every one of those screens belongs to somebody
else's ticket (PIL-337, 338, 340, 341, 342). The primitive is mine; the
conversions are theirs. Converting them here would have put my PR in conflict
with five others.

**One slice produced no production code.** I wrote keyboard-access tests
first and they passed immediately — Material's `NavigationRail` already
handles Tab traversal and Enter activation. Rather than invent a widget to
justify the slice, I kept the tests as regression cover and committed them as
`test(nav)`, not `green`, with the reason in the message.

## A regression I caused and fixed

My shell change broke 9 of 18 existing navigation tests.

The cause: `flutter test`'s default surface is **800×600**, and 800 is medium
under the new classification — so tests written for a bottom bar were handed a
rail. The tests were right; their unstated assumption about window size had
become wrong.

I fixed it at the shared `mount()` helper by pinning a phone viewport, and
committed that as a separate `refactor` so it is visible that the tests pass
because the assumption was corrected, not because the expectations were
weakened.

**Then CI found two more I had missed.** Two nasabah tests in files I had not
checked failed with `Found 0 widgets with type "BottomNavigationBar"` — same
cause, different files. I had told the user all nine local failures were
pre-existing; that was true of seven and wrong about two, and CI was right to
contradict me.

The fix is also worth recording because the obvious version was wrong: pinning
390×844 made those two pass and broke **eight** others in the same files, since
a phone width reflows the layout they inspect. Pinning 599×800 — compact by one
pixel, but close to the original 800 — fixed all of it. All fourteen pass.

## Known follow-ups

A review pass after the PR was already green surfaced two things I would rather
state than leave for someone else to find:

1. **Classification is width-only.** A phone in landscape (844×390) is
   `expanded` by width, so it gets a 256px rail on a 390px-tall viewport.
   Material's window size classes have a *height* class too, and I am not
   consulting it. Compact height should keep the bottom bar.
2. **The collapsed rail has no labels and no tooltips.**
   `labelType: NavigationRailLabelType.none` is set unconditionally, but it is
   only *required* when `extended` is true. At 720px that leaves five bare
   icons.

Neither is a reason to hold the PR, but both are real, and the first one is a
bug rather than a polish item.

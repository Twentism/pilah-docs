## The vulnerability I was not looking for

The plan was one header. Week 1's authenticated ZAP scan produced exactly
one real finding — no CSP anywhere — and the
[patch plan](s2-w1.md#b6-security) noted one wrinkle: the backend serves one
HTML page with an inline script, the Google OAuth popup, so a strict
`script-src 'self'` would block the page's own code and it would need a nonce.

Reading that page to add the nonce is what found the defect. It builds its own
HTML with an f-string, and `json.dumps` escapes neither `<`, `>` nor `/`:

```python
fallback = json.dumps(payload, indent=2)
html = f"""...
<pre>{fallback}</pre>
<script>
  const message = {message};
"""
```

Three values printed into that document, each injectable, with different reach:

| Sink | Reached by | Authentication |
|---|---|---|
| `<pre>{fallback}</pre>` | `?error=` | **none** |
| `const message = {…};` | `?error=` | **none** |
| `window.location.href = …` | `?next=` on `/start`, then its signed `state` | none, plus a round trip |

The first two need only a link, because `GoogleOAuthCallbackView` is `AllowAny`
and the first branch of `get()` passes `request.GET.get("error")` straight
through:

```
/api/v1/auth/google/callback?error=</pre><script>alert(document.domain)</script>
```

!!! danger "The third sink is the interesting one: a signature that legitimises the payload"
    `/start` checks only that `next` begins with `/` before signing it, then
    the callback reads that signed value into `window.location.href`. So an
    attacker calls `/start?next=/</script><script>…`, receives a **validly
    signed** `state`, and presents it to the callback.

    `TimestampSigner` guarantees integrity, not safety. It proves the server
    produced the value; it says nothing about whether the value is safe to
    print. The signature does not block this payload — it launders it.

**Why it survived.** `test_oauth_callback_error_param` already covered this
exact query parameter, and asserted `status_code == 400` and nothing else.
Nothing ever looked at the body. Every gate was green for as long as the page
has existed.

The reviewer confirmed this independently rather than taking the PR's word for
it: all three sinks were reproduced against the pre-PR code on `staging` and
[would genuinely execute](#the-review-round) `alert(document.domain)`.

### Positive, negative, corner

=== "Positive"

    [View](https://github.com/bank-sampah-PILAH/pilah-be/commit/21d62f5)

    **What happens in this case.** Someone sends a pengurus a link. Hidden
    inside the link is a piece of text written to look like code. Our page is
    meant to show that text as an error message, but it pastes it in without
    cleaning it first.

    One part of that text, `</pre>`, means "the message ends here". The browser
    believes it. Everything after that point stops being treated as a message
    and starts being treated as instructions, so the browser runs it. **That is
    the attack**: a stranger's code running inside our own site, the same site
    the login cookie belongs to. Nobody has to log in for this to work — the
    link is enough.

    The test asks for the page using that exact link, then looks at the message
    area. It checks that the two characters that begin a tag, `<` and `>`, are
    no longer there, and that the attacker's `</pre>` now appears as ordinary
    writing instead of as an instruction.

    ```python
    def test_blok_pre_tidak_bisa_ditutup_oleh_nilai_error(self) -> None:
        blok = self._blok_pre(self._popup(error=self.PEMBOBOL))
        self.assertNotIn("<", blok)
        self.assertNotIn(">", blok)
        self.assertIn("&lt;/pre&gt;", blok)
    ```

    The red state demonstrates the injection by accident, which is why it is
    quoted in the commit body: the test's own `</pre>` slicing stops at the
    **attacker's** closing tag, so the block it reads is a fragment.

    ```
    AssertionError: '&lt;/pre&gt;' not found in '{\n  "error": "'
    ```

=== "Negative"

    [View](https://github.com/bank-sampah-PILAH/pilah-be/commit/2dc77b9)

    **What happens in this case.** This one opens no page at all. It reads all
    four of our security rules and checks that one particular word is missing
    from each of them.

    What it protects against happens later, and by accident. One day a page
    looks broken, because the new rule is blocking something the page needs.
    The quickest way to make it work again is to add the word
    `'unsafe-inline'`. That does fix the page — and it also tells the browser
    "allow any code written inside this page", which is exactly what the
    attacker above needs. Nothing crashes, no warning appears, and the
    protection is simply gone. This test makes that shortcut fail straight
    away, while someone is still at their keyboard.

    ```python
    def test_tidak_ada_kebijakan_memakai_unsafe(self) -> None:
        for nama, kebijakan in SEMUA_KEBIJAKAN.items():
            with self.subTest(kebijakan=nama):
                self.assertNotIn("'unsafe-inline'", kebijakan)
                self.assertNotIn("'unsafe-eval'", kebijakan)
    ```

    The negative matters more than usual here because the easy wrong fix is
    `script-src 'self' 'unsafe-inline'`, which makes every page render and
    protects nothing. One `'unsafe-inline'` cancels the whole directive.

    It earned its keep in the review round: the obvious fix for the blocked
    developer pages was *exactly* the change this test exists to forbid, so it
    forced the nonce route instead — see [below](#the-review-round).

=== "Corner"

    [View](https://github.com/bank-sampah-PILAH/pilah-be/commit/154e44c)

    **What happens in this case.** We keep a list of the places a value can be
    printed into the page, and each place has its own cleaning rule. This test
    takes the attacker's text and runs it through every place on that list,
    checking that nothing dangerous comes out of any of them.

    The case it covers has not happened yet. One day someone will add a third
    place. Because the test reads the list instead of naming each place by
    hand, that new place is checked on the day it is added — not whenever
    somebody remembers to write a test for it.

    ```python
    def test_setiap_konteks_menetralkan_pembuka_tag(self) -> None:
        self.assertTrue(SEMUA_KONTEKS, "himpunan konteks tidak boleh kosong")
        for konteks in SEMUA_KONTEKS:
            with self.subTest(konteks=konteks.nama):
                hasil = konteks.loloskan({"error": PEMBOBOL})
                self.assertNotIn("<", hasil)
                self.assertNotIn(">", hasil)
    ```

    `assertTrue` is there for a quiet reason: a loop over an empty list
    finishes successfully without checking anything. If that list of places
    were ever emptied, this test would still pass while testing nothing at
    all. Same technique as the header registry in
    [Sprint 2 · Week 1](s2-w1.md#b1-test-driven-development).

    **A second case, from the other direction.** Making the text harmless
    must not change what it says. The test reads the cleaned text back out
    of the finished page and checks it still reads exactly as before. A
    "fix" that simply deleted the awkward characters would pass every other
    test here, and the pengurus would quietly be shown a different error
    message than the one Google actually sent.

### Proving the guards would actually fail

Six guards were added after green, so none had a red state. A test that has
never failed is not yet evidence, so each was checked by breaking the thing it
protects, one at a time, and restored afterwards.

| Mutation | Guard that caught it | Failure |
|---|---|---|
| escaping → dropping `<` and `>` | round-trip guard | `{'error': '/prescriptalert(document.domain)/script'} != {…}` |
| a careless third output context added | context iteration | `'<' unexpectedly found in '{"error": "</pre><script>…'` |
| `base_uri` dropped from the shared policy tail | every-policy loop | `'base-uri' not found in "default-src 'none'; …"` — fails for **all four** policies at once |
| `'unsafe-inline'` added to the page sources | no-unsafe loop | caught **only** in the CDN variant |

The last row is the one worth reading twice. The CDN variant of the page policy
is unreachable by any HTTP request in the suite, because Django's test runner
forces `DEBUG=False`. It is only covered because `SEMUA_KEBIJAKAN` calls the
builder directly. Without that line, half of `kebijakan_halaman` is untested
and this mutation survives.

## Test doubles: a stub at the transport boundary, and a configuration stub

Measured against the [three levels](s1-w3.md#test-doubles-what-is-faked-and-what-it-costs)
set out in Sprint 1 · Week 3, this week uses the two lowest and never the
highest.

**Level 0 — no double**, for every escaping and policy test. `KonteksKeluaran`
and `PembangunKebijakan` are pure functions over strings; there is nothing to
fake, and faking anything would only test the fake. Those cases simply hand
the attacker's text to the function and look at the text that comes back.
Nothing else takes part.

**Level 1 — a stub at the transport boundary**, for the one test that needs the
token-exchange path:

```python
token_response = Mock(status_code=400)
token_response.json = Mock(return_value={"error": "invalid_grant"})
with patch("apps.authentication.views.requests.post", return_value=token_response):
```

**What the stub actually does.** On this path our page normally has to ask
Google to confirm a login. A test cannot call Google, so the stub answers in
Google's place — and it answers the way Google really does when the login
fails. That failure is what makes our page show an error message, and showing
the error message is where the bug lives.

So the stub has one job: get the test to the broken line without using the
internet. It checks nothing itself, and it knows nothing about cleaning text.

Only the call to Google is faked. The real view, the real signer, the real
page-building code and the real middleware all still run — and that is what
makes the test worth having, because the bug is in the page-building code. Had
we faked anything higher up, the bug would have been hidden behind the fake.

**A configuration stub**, for the two admin tests, which must describe a
deployment that is not this one:

```python
@override_settings(STORAGES={..., "staticfiles": {"BACKEND": "...StaticFilesStorage"}})
```

**What the configuration stub actually does.** These two tests want to read
the security header that comes back with Django's admin page, so the page has
to be built first. Building it means looking up every style and script file the
admin uses. The real server prepares that lookup in a separate step we do not
run on a laptop, and without it the page refuses to load — so there is no
header to read at all.

The stub swaps that one piece of setup for a simpler one. It stands in for a
*server setting*, not for any part of the program: everything the request
actually touches is real.

**Implication.** It isolates configuration rather than collaborators, so it
costs none of the coupling a mock costs and buys none of the reach. It cannot
tell you the middleware is wired into `MIDDLEWARE` at all — only a real request
can, which is why the last check was a running server, and why a reviewer
reading `MIDDLEWARE` found something no test of mine had.

## Verified against a real server, not only the test client

Django's test client exercises the middleware stack but is not a socket, and a
header assertion is not a browser. So all three contexts were checked against
`runserver`:

```console
$ curl -D - http://127.0.0.1:8351/api/v1/auth/google/start
Content-Type: application/json
Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'

$ curl -D - "http://127.0.0.1:8351/api/v1/auth/google/callback?error=access_denied"
Content-Type: text/html; charset=utf-8
Content-Security-Policy: default-src 'none'; script-src 'nonce-So45c3faOv4WnoiB2i5kOQ'; ...

$ curl -D - http://127.0.0.1:8351/admin/login/
HTTP/1.1 200 OK
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; ...
```

Two further checks, because each is a way the feature could be wrong while
every test passes: the nonce in the header was compared against the nonce in
the `<script>` tag and matched — a mismatch blocks the page's own script and no
test notices — and `/static/admin/js/theme.js` answers 200, so `script-src
'self'` does not starve the admin of its own JavaScript.

This habit comes from the blank-white-page lesson in
[Part C](../part-c.md#sprint-1-week-3): a green check is not a working system.
Its limit is recorded under [what is not finished](#what-is-not-finished) —
curl reads headers, and a CSP that blocks something reports it in the console.

## B2 · Programming principles

### Strategy — one value, several output contexts

**Pattern: Strategy.** Commit
[`6bc9a6d`](https://github.com/bank-sampah-PILAH/pilah-be/commit/6bc9a6d),
module `shared_kernel/keluaran_dokumen.py`.

The three cycles closed three sinks. What they did not fix is the **reason**
there were three: nothing tied an escaping rule to the context a value printed
into, so the template author had to remember which was which — and that is what
failed three times in one function.

Each context becomes a named value carrying its own rule — `TEKS_HTML` and
`LITERAL_SKRIP`, both exposing `loloskan(nilai) -> str`. A sink picks a
**place** ("I am printing into a script"), not an **algorithm** ("I will use
translate").

```python
@dataclass(frozen=True)
class KonteksKeluaran:
    nama: str
    _aturan: Callable[[Any], str]

    def loloskan(self, nilai: Any) -> str:
        return self._aturan(nilai)
```

**What the pattern actually does.** The same piece of text lands in two
different places on one page, and it has to be written differently in each:

| Where it lands | Rule used | What gets written | Why it is harmless there |
|---|---|---|---|
| in the message area | `TEKS_HTML` | `&lt;/pre&gt;&lt;script&gt;…` | the browser reads it as writing, so nothing becomes an instruction |
| inside the page's own code | `LITERAL_SKRIP` | `\u003C/pre\u003E\u003Cscript\u003E…` | it stays ordinary data, and the browser never meets the characters that would end the code |

Swap the two and the page breaks. The first spelling is not valid data, so the
page's own code stops working. The second one, shown in the message area, gives
the pengurus a message full of strange characters. Both are safe; only one is
right in each place.

That is the whole reason the rule travels with the place. Whoever writes the
page says "this goes in the message area" and gets the matching rule, instead
of having to remember which rule belongs where — which is the thing that went
wrong three times in one function.

!!! important "Why Strategy and not something more impressive"
    A family of interchangeable algorithms behind one interface, selected by
    the caller according to situation. **Not Template Method** — no skeleton
    calls back into caller-supplied parts. **Not Decorator** — nothing wraps
    another object to add behaviour. Naming it accurately mattered, because an
    earlier delivery mislabelled Template Method work as "Strategy" and it had
    to be corrected on [`pil-340.md`](../../contributions/pil-340.md).

Alternatives rejected, stated in the commit body:

1. **One function with a `konteks="html"` argument.** The string is unchecked,
   so a typo silently selects the wrong escaper. For security code that is the
   worst failure mode: it looks right and emits an injectable document.
2. **Two free functions** — the shape at `51d227d`, mid-PR. Works, but names no
   contexts and makes the set uncountable, leaving exactly the memory burden
   that caused the bug.
3. **An abstract base class per context** — two classes for two pure functions,
   no state to hold.

What decided it was not tidiness but testability: `SEMUA_KONTEKS` made the set
iterable, which is what makes the corner-case test above possible at all.

### Builder — a policy assembled from directives

**Pattern: Builder.** Commit
[`e82b5ac`](https://github.com/bank-sampah-PILAH/pilah-be/commit/e82b5ac),
module `shared_kernel/csp.py`.

!!! danger "The fact that decides this design: CSP fails open"
    **Browsers ignore Content-Security-Policy directives they do not
    recognise.** Writing `frame-ancestor` instead of `frame-ancestors` produces
    a header that looks correct, passes any test matching on text, and protects
    nothing at all. A typo in a CSP directive name is invisible.

So directive names exist exactly once, inside `PembangunKebijakan`, and callers
use named methods — `bawaan`, `skrip`, `penyemat`, `base_uri`, `tujuan_form`. A
typo becomes an `AttributeError` at import instead of a dead directive in
production. `_penutup()` applies the three directives every policy must carry,
none of which inherit from `default-src`:

```python
def _penutup(pembangun: PembangunKebijakan, tujuan_form: str) -> str:
    return pembangun.penyemat(TIDAK_ADA).base_uri(TIDAK_ADA).tujuan_form(tujuan_form).bangun()
```

**What the pattern actually does.** Each step adds one rule to a list, and at
the end the list is joined into the single line the browser reads, in the order
the rules were added:

```python
PembangunKebijakan().bawaan(TIDAK_ADA).skrip(sumber_nonce(nonce))
# → default-src 'none'; script-src 'nonce-So45c3faOv4WnoiB2i5kOQ'
```

Two things happen here that writing that line out by hand cannot do.

The rule names are spelled in **one place only**, inside the builder, so a typo
stops the program immediately instead of producing a rule the browser throws
away. And adding the same rule twice is refused outright, because a browser
keeps only the first one and ignores the rest.

Those are the two ways a security rule can quietly do nothing at all. Both now
fail loudly, before the page is ever sent.

Alternatives rejected: **f-strings per policy** (the shape before this commit —
repeats directive names and copies the shared tail three times); **a dict per
policy plus one serialiser** (better, but callers still write directive names as
dict keys, so a typo is still a dead directive — precisely the failure mode
being designed against); **Abstract Factory** (no families of related products);
**Prototype** (nothing to clone).

The refactor is behaviour-preserving in the checkable sense: it touches one
file, and all four policy strings are byte-identical before and after, verified
by diffing them.

!!! note "The reviewer found the hole in the argument, and it was the same hole"
    The builder was designed so a *misspelled* directive cannot silently die.
    It still accepted the **same** directive twice, and browsers keep the first
    occurrence and drop the rest — so a second `script-src` dies just as
    silently as a misspelled one. The module existed to prevent that exact
    failure and permitted one form of it.

    `_tambah` now raises `ValueError` on a repeated directive name, with the
    reason in the message
    ([`cdb8fe7`](https://github.com/bank-sampah-PILAH/pilah-be/commit/cdb8fe7)).

### backend #132 — alghani46, search customers by full or partial ID

Adding `nomor` to the existing OR group rather than to the outer filter is the
right call, and the test that pins it is the valuable one:
`test_search_id_never_exposes_other_bank_even_with_same_id` creates the *same*
`nomor` in a second bank and asserts only the caller's row comes back, so the
new predicate provably cannot widen the access boundary. Rebuilding the
predicate as a named `search_filter` with one field per statement also reads
better than the old chained expression.

**The search path now does four unindexable scans per request, twice over.**
Production runs PostgreSQL (`DB_ENGINE=django.db.backends.postgresql` in
`.github/workflows/deploy-cloud-run.yml`), where:

- `icontains` compiles to `UPPER("nasabah"."nomor"::text) LIKE UPPER(%s)` with
  a leading `%`. The function call *and* the leading wildcard each
  independently rule out a b-tree. The only index covering `nomor` is the
  `unique_together ("bank_sampah", "nomor")` b-tree, usable for equality or
  prefix on the raw column and never for `%…%`.
- So a list request evaluates up to four `UPPER() LIKE '%…%'` predicates
  against every row in the bank's partition.
- `StandardPagination` (`PageNumberPagination`, `PAGE_SIZE = 20`) then issues
  `COUNT(*)` over the same filter before slicing the page, so that scan runs
  **twice per request**.
- `ORDER BY nomor` over the filtered set becomes a sort rather than an index
  walk, since the `(bank_sampah, nomor)` index is unusable once the OR group is
  in play.

The PR's own findings table reaches the same place — "Four substring predicates
and count queries may be costly … measure query plans and indexing needs" — but
defers it without a remedy, and this is the change that makes ID search, long
and digit-heavy, the common case rather than the rare one.

The fix was offered in two tiers so the author can take either.

**Index the substring search properly.** `pg_trgm` GIN is the only index type
that accelerates `%…%`, and because `icontains` wraps the column in `UPPER()`
the index expression has to match it:

```python
# apps/nasabah/migrations/00XX_nasabah_search_trgm.py
from django.contrib.postgres.indexes import GinIndex, OpClass
from django.contrib.postgres.operations import TrigramExtension
from django.db import migrations
from django.db.models.functions import Upper


class Migration(migrations.Migration):
    operations = [
        TrigramExtension(),
        migrations.AddIndex(
            model_name="nasabah",
            index=GinIndex(
                OpClass(Upper("nomor"), name="gin_trgm_ops"),
                name="nasabah_nomor_trgm_idx",
            ),
        ),
        # and the same for nama
    ]
```

with `django.contrib.postgres` added to `INSTALLED_APPS`. One caveat was given
with it rather than left for the author to discover: trigram indexes need
**three** characters to be selective and the search minimum is two, so a
`test_two_character_id_fragment_is_searched`-shaped query still falls back to a
scan. Raising the minimum to 3, or routing 2-character queries to
`istartswith`, closes that gap.

**Zero-migration version, if the extension is too much for this PR** — stop
running four predicates when the query shape already rules three of them out:

```python
if self.action == "list" and len(search) >= 2:
    if "@" in search:
        search_filter = Q(email__icontains=search)
    elif search.isdigit():
        search_filter = Q(nomor__icontains=search) | Q(no_hp__icontains=search)
    else:
        search_filter = Q(nama__icontains=search) | Q(nomor__icontains=search)
    qs = qs.filter(search_filter)
```

This was checked against their test file before being suggested, and it keeps
every case green: `000123` and `0012` are digits, so nomor + no_hp; `11110001`
hits the phone branch; `budi@example.test` hits email; `zx-999` and `budi` fall
through to nama + nomor, which is what
`test_query_matches_different_fields_without_duplicate_customers` needs. It
halves the per-row work with no extension and composes with the index later.

Also asked for: an `EXPLAIN (ANALYZE, BUFFERS)` for `status=aktif&search=0012`
against the 102-row demo set, pasted into the PR. At that size every plan looks
fine, which is exactly why the number is worth recording now rather than after
a bank imports a few thousand customers.

**Small nit:** `len(search) >= 2` counts raw characters, so a query of two
spaces passes the gate and runs the full four-predicate filter plus `COUNT(*)`
for a query that can only match incidentally. `search.strip()` before the
length check costs nothing.

### mobile #168 — alghani46, clarify customer ID search on mobile and web

Collapsing the hint into one `nasabahSearchHint` consumed by
`nasabah_page.dart`, `nasabah_table.dart` and `nasabah_search_bar.dart` is the
right shape — those three had already drifted into "Cari nama nasabah..." and
"Cari nama atau nomor...", and now they cannot drift again. The layout test is
also the good kind of corner case: a 30-character legacy ID at 390x844
asserting `maxLines: 1`, ellipsis, the ID below the name and at least 8px clear
of the balance. That is the model column limit rather than a comfortable
fixture. Extending the semantics assertion to `contains('ID: NAS-0002')` means
the new row reaches screen readers instead of only being painted.

**Superseded searches are discarded on the client but still executed in full on
the server, and this PR makes that the normal case rather than the exception.**
`searchNasabah` cancels `_jedaCari` and bumps `_listRequestGeneration`, and
`loadNasabah` drops the stale response at
`requestGeneration != _listRequestGeneration`. That protects correctness, and
the generation counter is the right mechanism for it. What it does not do is
stop the work: `NetworkService.get` accepts only `queryParams` and `headers`
and never a Dio `CancelToken`, so once the 300 ms pause has fired a request,
the HTTP call and the backend's four-`icontains` scan plus `COUNT(*)` run to
completion and the result is thrown away. `RetryInterceptor` compounds it — per
its own comment it "quietly retried once before the failure reaches state
handling" — so a superseded request that gets dropped can cost two backend
searches for a page nobody will ever see.

This matters more after the change than before it. Names are short and typed in
one burst; IDs like `NAS-0000000000000123` are long and typed with hesitations,
so a single ID lookup plausibly fires two or three full searches where a name
search fired one. The PR description already notes the notifier "does not
cancel database work already in flight" — that is the hook to actually do it.

The fix threads a `CancelToken` down the path the author already owns:

```dart
// lib/core/client/network_service.dart
Future<Response> get(
  String path, {
  Map<String, dynamic>? queryParams,
  Map<String, String>? headers,
  CancelToken? cancelToken,
}) async {
  ...
  Response response = await dio.get(
    environment.baseUrl + path,
    queryParameters: queryParams,
    cancelToken: cancelToken,
    options: options.copyWith(headers: headers ?? headersRequest()),
  ).timeout(globalTimeout);
```

then `final CancelToken? cancelToken;` on `GetNasabahParams`, passed through
`GetNasabahUseCase` to the repository and datasource, and in the notifier:

```dart
CancelToken? _pencarianBerjalan;

void searchNasabah(String query) {
  if (_searchQuery == query) return;
  _pencarianBerjalan?.cancel('kata kunci diganti');
  _pencarianBerjalan = CancelToken();
  _searchQuery = query;
  ...
}
```

Two traps were named with it, because both are the kind that turn a performance
fix into a bug: map `DioExceptionType.cancel` to a no-op in the failure
handling so a cancellation never paints `NasabahError` over a live list, and
make `RetryInterceptor` skip cancelled requests, or it will re-fire exactly the
request that was just cancelled.

**A second, cheaper one.** `_refreshActiveCount()` calls
`getNasabahUseCase.execute(const GetNasabahParams(status: 'aktif'))` and then
reads only `data.totalCount`, so it downloads a 20-row page with each row's
`saldo` serialized in order to display one integer.
`GetNasabahParams(status: 'aktif', pageSize: 1)` returns the same `count` for a
twentieth of the payload. It is on the search path too, via
`_reloadAfterMutation` whenever `_searchQuery` is non-empty.

**Nit:** the hint drops email, which the backend still matches
(`Q(email__icontains=search)`, kept for compatibility per the companion PR).
Reasonable as a deliberate simplification, but a Pengurus who pastes an email
will get results the hint says they should not — worth a line in the
description so nobody later "fixes" the backend predicate to match the hint.

!!! note "Reviewing both halves of one ticket, not one of them twice"
    These are two reviews, not one review restated. The backend finding is
    about what one request costs; the Flutter finding is about how many
    requests get issued for a single lookup. Either fix alone helps: the
    backend index without client cancellation still pays for discarded
    searches, and cancellation without the index still scans the table for the
    one search that survives.

the strictest policy applicable to the whole API, because serving that page
would have required `'self' 'unsafe-inline'` everywhere.

**Positive case** — Someone sends a pengurus a link. Hidden in it is text written to look like code. Our page is meant to show it as an error message but pastes it in without cleaning it. One part of that text, `</pre>`, means "the message ends here" — and the browser believes it. Everything after that stops being a message and becomes instructions, so the browser runs it. *That is the attack*: a stranger's code running inside our own site, the same site the login cookie belongs to. Nobody has to log in; the link is enough.

**Negative case** — This one opens no page at all. It reads all four security rules and checks one word is missing from each. What it guards against happens later, by accident: a page looks broken, and the quickest way to fix it is to add `'unsafe-inline'`. That does fix the page — and also tells the browser "allow any code written inside this page", which is exactly what the attacker needs. Nothing crashes, no warning appears, and the protection is gone.

**Corner case** — We keep a list of the places a value can be printed, each with its own cleaning rule. The test runs the attacker's text through every place on the list. The case it covers hasn't happened yet: one day someone adds a third place, and because the test reads the list rather than naming each place by hand, that new place is checked the day it's added.

**Transport stub** — Our page normally has to ask Google to confirm a login. A test can't call Google, so the stub answers in its place, the way Google really answers when a login fails. That failure is what makes our page show an error message — and the error message is where the bug lives. The stub's only job is to get the test to the broken line without using the internet.

**Configuration stub** — The tests want to read a header off Django's admin page, so the page must be built first. Building it means looking up every style and script the admin uses, and the real server prepares that lookup in a step we don't run on a laptop — without it the page refuses to load, so there's no header to read. The stub swaps that one piece of setup for a simpler one. It stands in for a *server setting*, not for part of the program.

**Strategy** — The same text lands in two places on one page and must be written differently in each. Swap them and the page breaks: one spelling isn't valid data so the page's own code stops working; the other, shown in the message area, gives the pengurus a message full of strange characters. Both are safe, only one is right per place — which is why the rule travels with the place instead of being remembered by hand.

**Builder** — Each step adds one rule to a list, joined at the end into the single line the browser reads. Two things that writing the line by hand can't do: rule names are spelled in one place only, so a typo stops the program instead of producing a rule the browser throws away; and adding the same rule twice is refused, because a browser keeps the first and ignores the rest. Those are the two ways a security rule can quietly do nothing.

# PIL-293 — responsive layout and web navigation shell

## The problem

The Pengurus app had exactly one navigation form: a bottom navigation bar.
That is correct on a phone. On a 1440px monitor it puts the primary navigation
as far from the user's attention as the screen allows, and leaves content
stretched across the full width with no reading bound.

## The rule

**In the app the navigation sits at the bottom. In a browser it sits on the
left.** That is the lead dev's rule, and it is the right discriminator:
*platform* decides the family, and width only decides how much of the
left-hand navigation fits.

| Platform | Width | Navigation | Content |
|---|---|---|---|
| app | any | bottom bar (unchanged) | full width |
| browser | `< 600` | menu button → drawer | full width |
| browser | `600–839` | collapsed rail, labels under icons | full width |
| browser | `>= 840` | labelled rail + bank sampah name | capped at 1200, centred |

The boundary belongs to the wider block: 600 and 840 each belong to the block
above them, pinned by on-point tests rather than stated in a comment.

!!! warning "I got this wrong first, and the rule is why"
    My first version decided everything from window width alone. That is wrong
    in **both** directions: a native phone held sideways is 844px wide and lost
    its bottom bar, while a browser window narrowed below 600 grew one.

    Deciding on `kIsWeb` instead removed the landscape bug by deletion rather
    than by patching — native is never a rail, so there is nothing left to
    guard. The fix I had planned (adding Material's window *height* class as a
    second dimension) would have been more code for a worse answer.

## The design decision I am most confident about

I extracted `RoleDestinations` **before** adding the rail, as its own red-green
pair, and left `RoleNavigationBar`'s render path byte-for-byte unchanged.

That ordering is the whole point. The bottom bar is the form that already works
for every member on a phone; adding more forms should not be able to disturb
it. Afterwards, *which* destinations a role has is decided in exactly one
place, and *how* they are drawn belongs to each widget — Single Responsibility,
and Open/Closed in the sense that matters here.

It paid off twice, not once. The rail was added without modifying the bar; then
the drawer was added without modifying either. Three navigation surfaces, one
source of destinations.

It is also the security argument — see [Security](../ir/b/s2-w1.md#b6--security).

## Input Space Partitioning

Two inputs, so two partitions. Platform is binary; width is continuous and gets
on-point and off-point tests.

| Partition | On-point | Off-point |
|---|---|---|
| drawer (web) | 599 | 600 |
| collapsed rail (web) | 600, 839 | 599, 840 |
| labelled rail (web) | 840 | 839 |
| bottom bar (native) | any width | — |

Plus degenerate input: a non-positive width returns the narrowest form rather
than throwing, because the first frame can run before the window size is known.

Native is tested at three widths — 390, 820 and **844×390** — precisely because
width must *not* change the answer there.

## Three judgement calls to defend

**No grid primitive.** The dashboard stat cards are already a fixed 3-across
`Row` with `IntrinsicHeight`. Their actual desktop problem was unbounded width,
and `ContentBounds` solved that. A grid would have been an abstraction with no
caller.

**Zero `MasterDetailLayout` call sites.** Sixteen screens still open details as
modal bottom sheets, and every one of those screens belongs to somebody else's
ticket (PIL-337, 338, 340, 341, 342). The primitive is mine; the conversions
are theirs. Converting them here would have put my PR in conflict with five
others.

PIL-340 vindicated this: its ticket asks for *"detail transaksi sebagai dialog
atau panel"* and *"state loading, dan error"* — `MasterDetailLayout` and
`PageStateView`, the two primitives shipped with no callers.

**One slice produced no production code.** I wrote keyboard-access tests first
and they passed immediately — Material's `NavigationRail` already handles Tab
traversal and Enter activation. Rather than invent a widget to justify the
slice, I kept the tests as regression cover and committed them as `test(nav)`,
not `green`, with the reason in the message.

## Regressions I caused, and how each was caught

**Nine navigation tests, caught locally.** `flutter test`'s default surface is
800×600, which the new classification called medium — so tests written for a
bottom bar were handed a rail. The tests were right; their unstated assumption
about window size had become wrong. Fixed at the shared `mount()` helper and
committed as a separate `refactor`, so it is visible that the tests pass
because the assumption was corrected, not because expectations were weakened.

**Two more, caught by CI.** Two nasabah tests in files I had not checked failed
with `Found 0 widgets with type "BottomNavigationBar"`. I had told the team all
nine local failures were pre-existing; that was true of seven and wrong about
two.

The fix is worth recording because the obvious version was wrong: pinning
390×844 made those two pass and broke **eight** others in the same files, since
a phone width reflows the layout they inspect. Pinning 599×800 — compact by one
pixel, but close to the original 800 — fixed all fourteen.

**Then all of that pinning was deleted.** Once platform decided the form,
`kIsWeb` is `false` in `flutter test`, so native-shaped tests get the bottom bar
at any surface size. Every viewport pin was a workaround for a decision made in
the wrong place, and the right fix removed the need for all of them.

## A test I deleted for passing

While fixing the collapsed rail's missing labels I wrote a test asserting the
label text appears on screen. It passed **before** any fix: with
`labelType: none` the text is still in the widget tree, just not painted, so
`find.text` cannot tell the two states apart.

A test that passes before the change is not testing the change. I deleted it
rather than keep a false guarantee, and said so in the commit. The assertion on
`labelType` does discriminate, and that is what remains.

!!! note "A blocker that turned out not to be one"
    I reported the Android build as blocked by a missing
    `android/app/google-services.json`. That was true but misleading: the build
    is not broken, it only needs the config file *present*. With a local
    placeholder it builds fine, because `Firebase.initializeApp()` is the only
    Firebase call in the whole of `lib/` — `firebase_auth` and
    `firebase_crashlytics` are declared in `pubspec.yaml` and never imported.

    "Blocked" and "needs a file I do not have" are different claims, and I made
    the stronger one.

## Browser QA

Debug build, local backend, demo login as Pengurus, real data. All four forms
checked on a running app, plus a functional click to prove the menu-index to
branch-index mapping is right — the two are *not* the same number, and
conflating them has caused navigation bugs here before.

- **1440×900** — labelled rail, header shows the bank sampah name
- **720×900** — collapsed rail, each icon now captioned
- **390×844** — hamburger button, no rail and no bottom bar
- **390×844, drawer open** — bank name header, five labelled destinations,
  current one highlighted; selecting one navigates and closes the drawer

Zero Dart console errors. The only console output is Google Identity
complaining about an empty local `client_id`.

Native behaviour is covered by the three tests above rather than verified on a
device. An emulator needed a 929 MB AVD and did not finish booting in a
reasonable time, so a physical phone over USB — rotated to landscape, which is
the actual bug case — is the one check still outstanding before merge.

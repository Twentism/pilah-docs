# Sprint 1 · Week 1

**15 – 21 September 2026** · backend only · PIL-168, PIL-224

Two tickets, both in `pilah-be`, both about refusing bad numbers before they
reach the ledger.

| Ticket | What it does |
|---|---|
| **PIL-168** | Rupiah is a whole number and rounds **down**, everywhere |
| **PIL-224** | Deposit weight limits, and waste types with no usable price |

## B1 · Test-driven development

Every behaviour arrived as a failing test first. The 20 September run:

```
test(transaksi): add failing test for rupiah rounding
feat(transaksi): round deposit values down to whole rupiah
test(transaksi): add failing test for client-supplied price
feat(transaksi): reject client-supplied item price
test(transaksi): add failing test for legacy balances with sen
feat(saldo): round legacy balances down when updating
```

and 21 September:

```
test(transaksi): add failing test for 1000 kg deposit weight limit
feat(transaksi): limit deposit weight to 1000 kg
test(transaksi): add failing test for 500 kg item weight limit
feat(transaksi): limit item weight to 500 kg
test(transaksi): add failing test for waste type without usable price
feat(transaksi): reject waste types without a usable price
refactor(transaksi): derive weight limit messages from constants
```

Note the `refactor` arrives **after** the three cycles are green, not between
them. That is the shape the convention is meant to produce.

**Boundary cases.** Weight limits are a continuous input, so they are tested on
both sides of each edge rather than at a comfortable value:

| Partition | On-point | Off-point |
|---|---|---|
| item weight | 500 | 500.01 |
| deposit total | 1000 | 1000.01 |
| price | smallest usable | zero, missing |

Zero and negative weight are the degenerate cases, and a waste type with no
usable price is the "valid shape, unusable content" case — the one that is easy
to forget because the row exists and looks fine.

## B2 · Programming principles

**Single Responsibility.** Rounding is one rule, so it lives in one place:
`shared_kernel/kalkulasi.bulatkan_rupiah`. It began as a fix inside one view
and was extracted so the deposit path, the balance path and the history path
could not drift apart.

**Don't repeat the rule.** `refactor(transaksi): derive weight limit messages
from constants` exists because the limit was stated twice — once as a check and
once as an error string. Two statements of one number is a defect waiting for
someone to change one of them.

## B3 · Development discipline

Conventional Commits throughout, scoped, imperative, no trailing period. Bodies
explain *why* the rule is what it is, which matters here because
"round down, never to nearest" is a product decision and not an obvious one.

`style(api): apply ruff lint and format fixes` is kept as its own commit rather
than folded into a feature commit, so the functional diff stays readable.

## B5 · Code quality

`ruff`, `ruff format`, `mypy --strict`, `makemigrations --check` and the Django
test suite, all green before pushing. Backend coverage reached 100%.

## B6 · Security

**A04 · Insecure Design** — *mine.*
`feat(transaksi): reject client-supplied item price`. The client used to be
able to send an item price. It cannot any more: the server fills each item's
price from the master *jenis sampah* record and ignores anything the client
sends. A price arriving from the client is not a validation problem to be
tightened, it is a field that should not exist — so it was removed rather than
checked.

That one change is also why PIL-340's web form can safely show a running total
six months later: the figure on screen is explicitly a display estimate, and
the server's number is the one that moves the balance.

## What I would do differently

The rounding rule was discovered mid-ticket from a conversation with Tristan,
not from the PRD. The notes on PIL-138 implied `ROUND_HALF_UP`. Had I started
from the written spec alone I would have shipped the wrong rule — which is an
argument for asking, not for reading more carefully.
